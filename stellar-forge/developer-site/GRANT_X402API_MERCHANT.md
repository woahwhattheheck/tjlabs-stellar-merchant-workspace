## Merchant invoices, paid fulfillment and portable operating projects

The merchant workspace gives an operator a complete path from a priced service request to a retained payment record, delivered file and reopened operating project. It is useful when a merchant sells a report, data extract or another completed resource, and when an implementation partner must hand the running service to the customer's operator. The invoice, payment request, authorization, settlement observation, delivery edition and result remain attached to the same business record.

This is an implemented operating foundation for the existing Stellar Forge programme. Its completed commissioning used five local x402api protocol fixtures, including Base USDC and Solana payment-term vectors. Those fixtures exercised the actual application, HTTP, SQLite and cryptographic verification code; they did not submit real payments. The grant's separate development baseline remains **18 actual Stellar purchases and 0.0411 XLM**. The five local invoices do not change that baseline or the independent merchant and buyer targets.

### The operator and buyer journey

An operator connects to the merchant's invoice desk with the private operator token, enters a business reference and description, and selects exact prices on the configured payment rails. The application converts decimal display prices to canonical atomic-unit amounts without floating-point rounding. Each invoice freezes its resource and wallet versions, recipient, asset and network terms, protected request, and selected fulfillment edition. Later changes to a product file or configuration do not silently change an outstanding invoice.

**Create payment request** retains the original charge and produces a downloadable wallet request containing the unchanged payment requirement and protected request. The buyer's compatible wallet integration returns the complete authorization. The operator can receive that authorization, or the buyer can submit the original protected request directly. The server retains the authorization before making its first empty upstream payment POST. Payment refresh and recovery continue that invoice and its original request.

The service receives the configured ownership challenge and authenticates webhook bytes before interpreting their payload. It verifies a finalized receipt using separately configured signing-key fingerprints and the invoice's original payment, order, resource and selected price bindings. The browser does not hold the tenant credential or webhook secrets. The operator token remains in browser memory and is cleared on disconnect; server credentials continue to use the deployment's existing environment references.

Once the selected payment is verified, the configured fulfillment adapter supplies the useful result. The original file adapter returns the exact content-bound file edition; it retains earlier editions for earlier invoices. A customer-specific handler receives the original payment ID as its idempotency key and supplies its own authoritative reconciliation for external work. The application retains returned result bytes before publishing the complete file through the original SF31 writer. Every download uses the original SF88 verified-file reader to check the retained size and SHA-256.

The invoice desk exposes the saved request, payment and delivery progress, activity history, wallet request and completed download. The HTTP interface serves the same records used by the browser. Reopening an existing project keeps its completed invoices, authorizations, authenticated events, fulfillment records and original result files.
