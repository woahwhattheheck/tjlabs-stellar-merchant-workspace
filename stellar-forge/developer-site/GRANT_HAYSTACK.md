## Haystack building models: reviewed point lists, validation and contractor handover

A building integrator receives point lists whose identifiers, names, units and equipment descriptions were authored by different people or systems. A contractor may correct names and relationships and return a later model while the receiving engineer has continued working. The useful output is the complete reviewed model, its original source associations, native validation evidence and an editable handover that preserves both parties' work. A changed label, duplicate heading or interrupted report must not silently change the point's identity or erase the source behind a decision.

The maintained Haystack product now supplies that workflow alongside its original typed-grid and corrective-work application. It imports complete original CSV/TSV files or selected native Haystack grids, previews explicit column and naming choices, saves full semantic model versions, and prepares native Brick models and contractor handovers. The actual standard is the original Brick 1.4.4 distribution with its included REC vocabulary. Node serves the workspace, browser, HTTP/CLI/MCP operations and durable request history; the selected offline Python environment supplies the original CSV reader and Brick/RDFLib/pySHACL engine. Building records, model files and private customer evidence remain off-chain.

### Complete implemented source and operator controls

The [point-list modelling guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/5ff96cd9c03f2cef99284cd4c96daf0c6e96cc96/stellar/scf-starforge-20261009/sf30-seller-sdk/haystack-workspace/SEMANTIC_MODELLING.md) and [installed operating guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/5ff96cd9c03f2cef99284cd4c96daf0c6e96cc96/products/haystack/OPERATING.md) describe the complete merged application.

1. **Receive original sources.** Native CSV inspection retains UTF-8 bytes, BOM, every column position and exact heading, every cell as text, each logical row index and its physical end line. Duplicate/blank headings and unequal row widths remain observations. Limits are explicit: 32 MiB, 25,000 data rows and 256 columns. Inputs beyond these limits fail without a shortened accepted result. The [original Haystack contract](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/5ff96cd9c03f2cef99284cd4c96daf0c6e96cc96/stellar/scf-starforge-20261009/sf30-seller-sdk/haystack-workspace/HAYSTACK_CONTRACT.md) and [Charlie example](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/5ff96cd9c03f2cef99284cd4c96daf0c6e96cc96/stellar/scf-starforge-20261009/sf30-seller-sdk/haystack-workspace/fixture-charlie.json) preserve the native grid's source meaning and existing record keys.
2. **Preview mappings and names.** An operator chooses ID, name, kind, equipment, site and unit columns by position. Naming templates propose names using selected source tokens. Initial entity IDs derive from original source kind, source ID and row index; duplicate labels or external identifiers remain distinct. Stable entity IRIs retain those identities when a label changes. The original source is not renamed by a proposal.
3. **Review the complete model.** Saved content includes all entities, relations, dictionary definitions, class/tag/property IRIs, typed literal forms, source references, notes and separately recorded physical observations. The operator declares actual entity relationships; matching equipment-name text does not invent a physical connection. Unclassified entities, unmapped/reused rows and unknown terms remain visible.
4. **Save against the opened head.** Each complete model version retains its content/source-context hashes, parents, author, time and reason. Both the opened model head and original workspace revision are checked. Browser drafts, incomplete JSON, open forms, selected files and pending requests are retained. A concurrent edit leaves the draft available for explicit comparison and resolution.
5. **Validate the selected version.** The [native standard guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/5ff96cd9c03f2cef99284cd4c96daf0c6e96cc96/stellar/scf-starforge-20261009/sf30-seller-sdk/haystack-workspace/SEMANTIC_NATIVE.md) binds the exact original ontology and engine. Validation receives the selected model/version/content identity and retains a separate digest for its full native projection. The model never supplies executable replacement shapes, remote imports or returned application code. Validation and mapping review are separate decisions.
6. **Review returned work.** A full returned workspace is checked for original application, source, content, ancestry and output identities. For every returned model, the reviewer chooses Keep local or Adopt returned. Adoption of an existing model creates a version with both original heads as parents. Keeping local preserves the contractor's full source, versions, reviews and reports without changing the active model. Later export carries that combined history.
7. **Continue original corrective work.** The same workspace retains the [corrective-work procedure](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/5ff96cd9c03f2cef99284cd4c96daf0c6e96cc96/stellar/scf-starforge-20261009/sf30-seller-sdk/haystack-workspace/CORRECTIVE_WORK.md): original findings, assigned work, reviews, deliberate corrections, source evidence and returned history. Semantic proposals remain connected to original points without replacing their native records or the separate corrective-work decisions.

The full source includes 21 semantic actions in the normal action catalogue and the original merchant tool interfaces, full-file delivery/range mechanisms and Applications contribution. The managed application uses its existing private environmentFile to select HAYSTACK_SEMANTIC_PYTHON and opens the same modelling route. Actual managed Start/Stop receiving remains dependent on the original READY runtime selection; the source join is not recorded as a completed installed lifecycle.
