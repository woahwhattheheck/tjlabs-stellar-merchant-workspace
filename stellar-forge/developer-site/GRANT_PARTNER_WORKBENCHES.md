## Mobility and education managed workbenches

Two original staff products now use the same maintained source, Workshare, Installation, Applications and Merchant foundation. The mobility product carries complete monthly publications into comparisons and source-backed findings. The education product carries exact course, pathway and framework editions into reviews and corrective actions. Each retains its own original workspace identity, source records and business history.

### Mobility source review

#### Customer work and useful result

A mobility team needs to understand a complete published operating period before it can use the data in a service review or implementation decision. The useful unit of work is a reviewed source edition and its resulting analysis: the complete monthly publication, explicit field interpretation, retained quality findings, a comparable-period analysis, station flows, working review notes and the editable delivered workspace.

The implemented mobility workbench carries those pieces in one source-based staff application. It preserves the original published bytes alongside the selected import interpretation and records. Operators can reopen the precise edition that produced a finding, compare selected imports, inspect station flow and maintain review notes with complete record history. Markdown and CSV reports are accompanied by the complete runnable workspace archive.

The Installation profile is `mobility-source-review`; the managed Applications entry is `partner-mobility`. Their maintained source is [the full mobility workorder profile](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/ae97decd04f04b2ffc1989498140c9cbefec502e/stellar/scf_2026/sf49_data_commissioning/installation-workorders/mobility-source-review.json). The profile describes the original customer course, source population, useful output, receiving procedure, maintenance ownership and repeat trigger. The commissioned scope is supplied by the selected original Workshare.

#### Original source and period interpretation

The original source product retains full monthly mobility publications and their source metadata. Import interpretation belongs to the original product; the managed integration receives its complete application and archived state. The source URL, file identity, selected field mapping, calendar period, import identity and original record history remain available together.

A comparison selects between two and twelve actual retained imports. The analysis uses the original product's calendar-day method and station-flow calculation. The comparison output keeps its selected import IDs so an operator can distinguish a source revision, another city or another month from a change in the analytical result. Review notes retain the supporting source and revision that the operator actually selected.

The original source/browser programme selects complete Oslo and Bergen September 2026 monthly publications. It receives them into the original product before any installation handover. That defined receiving programme is the source of its future measured row totals, source response identities and native outcomes; those counts are not inferred from the installed adapter.

| Working item | Retained meaning | Operator use |
|---|---|---|
| Monthly source edition | Complete original file, source metadata and selected interpretation | Reopen and inspect the publication used by the analysis |
| Import | Original import identity, mapped fields, valid and invalid rows and period | Review the complete intake and quality findings |
| Comparison | Explicit selected import IDs and original calculation | Compare actual periods and inspect the difference |
| Station analysis | Original source-backed station flows | Examine the selected import without mixing a later edition |
| Review note | Original source linkage, record ID and complete revision history | Record and revise findings with their supporting context |
| Delivery | Original report, CSV and full runnable workspace/application | Hand useful work to an independent operator |

#### Commercial work becomes an original Installation

The generic profile receives the actual Workshare, phases, funding choices, acceptance checks and source-use decisions from the existing case. A commission is prepared through [the maintained partner commissioner](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/ae97decd04f04b2ffc1989498140c9cbefec502e/products/partner-workspace/commission.mjs), which reads the original Installation seed, original bindings and exact source selection.

The commissioner checks that the selected case and Workshare case match the original seed, that the source attachment is present in the same original bindings, and that the full source manifest belongs to the mobility product. It calls the existing profile loader and Installation preparation function. The prepared workorder, Workshare and checks are compared with the original seed before the complete output is published.

The output includes the unchanged original seed, bindings and source selection, the prepared Installation document and preview, the whole workorder, and the exact native preparation request. The original operator uses the maintained preview/save flow. Private company fees, contacts and original commercial dates remain in that selected case; the reusable profile supplies the product and receiving procedure.

A source fee, merchant purchase or Stellar-funded activity remains part of the original selected commercial work. The actual authorization, payer, price, source output and receiving check must be present in that case when used. The mobility adapter itself operates the retained application and source records; a file count or retry is not a new commercial unit.


#### A complete mobility course

1. Select the original Workshare and Installation case, its source bindings and the complete original runtime manifest. Select the saved original workspace archive when continuing an existing case.
2. Prepare the immutable source edition and original workspace with one retained request ID. Inspect the product, source identity and workspace UUID.
3. Save and review the Mobility source review entry in Applications, start the original server and open its actual local URL.
4. Inspect original publications, their field interpretation and source quality. Select the actual comparable imports; inspect calendar-day comparison and station flows.
5. Create or revise the original source-backed finding in the staff editor, inspect its complete history, and retain the useful original report and CSV.
6. Stop and reopen the same managed entry, confirming that the selected original workspace and records persist.
7. Stop the application for a complete original workspace export and installation snapshot. Retain the exact original request IDs and output identities.
8. Independently receive the complete installation, open the mobility application under its new installation identity and original workspace UUID, inspect the retained records and continue ordinary work.
9. Export onward from that received installation, keeping the original source, edited state and prior installation lineage.

This course follows the original product's APIs. The integration adds no parallel source store, note database or business queue.

### Education quality review

#### Customer work and useful result

An education team needs a review that can be reopened against the exact course, pathway, framework and evidence it assessed. The useful result includes the original publication facts, the selected edition of every pathway member, criterion decisions and reasoning, source-linked corrective actions, complete history and a runnable editable handover.

The implemented education workbench carries course and pathway records, framework criteria, reviews and corrective actions in one staff application. Reviews retain their exact parent course and framework revisions. Pathway reviews additionally retain the full selected child-course revision map and complete child snapshots. A later change can therefore be shown as a change in the reviewed context instead of silently altering what an earlier review meant.

The Installation profile is `education-quality-review`; the managed Applications entry is `partner-education`. Their maintained source is [the full education workorder profile](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/ae97decd04f04b2ffc1989498140c9cbefec502e/stellar/scf_2026/sf49_data_commissioning/installation-workorders/education-quality-review.json). The original customer Workshare supplies the actual scope, source rights, commercial assignments and acceptance decisions.

#### Original publications and exact review context

Course records preserve original availability and complete publication facts. A listing, removed course, revised publication and an operator's review decision have different meanings. The editor retains the saved availability value rather than upgrading a published listing when unrelated fields change.

The original education source programme includes nine course slots and two pathways from the selected publications. It preserves the explicitly removed Digital Twin course and original differences between provider and Campus descriptions, durations and certificate conditions. Those source facts are retained separately from review conclusions. Provider certificate conditions remain publication facts; learner issuance and programme eligibility require their actual responsible process.

A review selects the actual course/pathway edition and framework edition. For a pathway it also selects every current child course revision. The application keeps the exact map and full child snapshots with the saved review. Its current-context display shows when a parent, framework or child edition has changed. Starting a current-edition review is an explicit operator action; the older review and its original evidence remain intact.

Corrective actions bind to an exact review ID and revision. The staff interface displays that linkage and offers an explicit current-review selection when an action needs to move to a later review. Existing actions retain their original linkage until the operator changes it. A concurrent edit cannot silently rebind a saved action to a different review.

| Working item | Retained meaning | Operator use |
|---|---|---|
| Course publication | Complete original facts, availability, evidence and record revision | Compare a current publication with the originally reviewed edition |
| Pathway | Original membership and selected member revisions | Review the complete course group and identify changed or removed members |
| Framework | Exact criteria and saved framework revision | Explain the requirements actually used in a review |
| Review | Parent/framework revisions, child snapshots, criterion decisions and evidence | Reopen the same assessment and explicitly begin its successor |
| Corrective action | Exact review revision, owner, date, status and note history | Continue follow-up without changing the original assessment context |
| Delivery | Whole review report, CSV and complete original runnable workspace | Transfer the editable reviewed work and its supporting source |

#### Staff editor and interrupted work

The complete staff editor preserves working drafts and their source contexts while a user moves between records. A review draft's context includes the complete child revision map. Returning to another edition restores that draft's actual inputs; selecting the current context is explicit.

Saved revisions and action updates use the original expected revision. When a response is interrupted, the client inspects the actual saved history and compares the complete intended body before receiving that result. Concurrent changes remain available for review against the original base. History, source evidence and complete archive downloads use the original application APIs.

The receiving procedure exercises both the initial review and a current-edition successor, then the original action and an independent restored edit. Its receiver checks both complete preserved history and every original current record head. A received record cannot disappear or rewind to an older saved revision merely because that earlier revision remains in history.

The original Workshare supplies the scope, phased effort, fees, commercial dates or active business-day schedule, source-use choices and customer acceptance. The generic education profile keeps those selections separate from its reusable product definition.

The maintained [commissioner](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/ae97decd04f04b2ffc1989498140c9cbefec502e/products/partner-workspace/commission.mjs) reads the original Installation seed and source bindings. A partner's original commercial plan stays in its private case and enters the normal Workshare and accounting surfaces when selected; the public profile embeds no company-specific pricing or contact data.

### Shared installed operation and independent receiving

The implementation is part of the maintained merchant workspace at [the complete operating guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/ae97decd04f04b2ffc1989498140c9cbefec502e/products/partner-workspace/SCF.md). Its source-selected installation preserves the original application and database, while the existing Customer Installation, Applications and Merchant surfaces make that application usable by another operator. The project selected two separate product identities, `mobility` and `education`, with a shared installation mechanism. Customer source material, private configuration, commercial records and completed workspaces remain in their original private cases.

The application is prepared from a complete original runtime manifest, including its license and relative dependencies. Every member has its original byte count and SHA-256. The preparation copies those exact files into an immutable edition and restores a selected original whole-workspace archive, or intentionally creates the original empty workspace. A restored workspace retains its original UUID, product, evidence and revision history. The installation receives its own UUID so the producing installation and the independently received one can be distinguished without inventing a second business case.

The existing Applications supervisor starts the original Python service directly. Readiness is bound to the actual child process, selected Python, installation, workspace, immutable source edition and original loopback server announcement. The original application's Host and Origin checks remain in force. The staff browser is the writer for domain work; the typed client, CLI and fifteen Merchant tools inspect the same records and perform the named installation and delivery operations.

A stopped application can adopt a complete runtime successor against the same saved workspace. Earlier source editions and the exact original named operation remain available. Whole workspace export carries runnable application source, the database snapshot and selected original objects. The additional installation ZIP carries all source editions and lifecycle lineage. Independent receiving assigns a new installation UUID, preserves the original workspace UUID and reopens the actual application. A further export and receiving step carries that history onward.

The current source includes the complete original-to-installed receiving programme. It selects the existing source programme's final independently edited archive by default, validates every source and archive member, prepares the managed application, exercises its actual interface, exports useful original outputs, independently receives the installation and reopens it, and performs onward export. The same-case receiver retains its original operation, inputs, request IDs and current attempt result across interruption. Its source is published; the original source/browser programme and this installed continuation await their equipped host's actual execution. The grant's operating evidence should advance from that original result when returned.
