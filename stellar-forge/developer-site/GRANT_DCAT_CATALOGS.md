## DCAT catalogue migration, accepted editions and recurring customer delivery

The catalogue migration application gives a data publisher or implementation partner a practical way to prepare a source catalogue, explain its changes and hand the complete reviewed project to another operator. It is part of the existing merchant workspace. Its contribution to the Stellar programme is a usable data preparation and operating capability that merchants can incorporate into a useful customer service. The completed source engineering and GSA migration exercise are pre-award work. The funded programme remains the existing merchant integration, customer delivery, facilitator interoperability and launch work.

A catalogue release is the operator's decision about a particular reviewed document. Payment authorization, Stellar settlement and delivery of a purchased resource remain the responsibility of the existing merchant and facilitator components. The grant milestones join those components to an actual customer use case, with the existing useful-purchase and independent-operator criteria.

### A complete catalogue job

The [installed migration procedure](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/58ce16a5eca080b6f082d2db884ac55f34f67cc3/stellar/scf-starforge-20261009/sf30-seller-sdk/ckan/MIGRATION_OPERATING.md) follows the job from the original document to an independently receivable project. An operator receives a complete DCAT-US 1.1 or 3.0 catalogue, retains its original bytes and selects the source, optional comparison edition and any independently edited candidate. The original GSA converter and selected schemas perform conversion and validation. The review also follows catalogue members, identifier relocations, typed identity mappings and complete field changes. An already-3.0 document can be preserved byte for byte; flat-3.0 normalization is an explicit selection.

The saved review distinguishes source validation, candidate validation and conservation. It retains corrections-needed results as working material, including a conversion report that has no candidate. The operator can inspect full record values and every page of findings, download the original documents and report, correct a candidate or an identity decision, then prepare another review. Original inputs and preceding reports stay available throughout this process. Exact JSON handling preserves the source's numeric values when identifiers or field values exceed ordinary JavaScript number precision.

An accepted release selects the exact reviewed candidate and records its predecessor. Cutover binds the inspected active release and candidate/review hashes. Rollback creates a new entry selecting an earlier candidate, retaining the intervening reviews and decisions. The complete workspace archive carries documents, findings, corrections and release history to the receiving operator. The [original runtime and conversion guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/58ce16a5eca080b6f082d2db884ac55f34f67cc3/stellar/scf-starforge-20261009/sf30-seller-sdk/ckan/DCAT_ENGINE.md) describes the converter, schema selection, validation and complete report; the [installed package entrypoint](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/58ce16a5eca080b6f082d2db884ac55f34f67cc3/products/ckan/PACKAGE_README.md) connects the same project to Applications, commands and operating guides.

The browser, command line and merchant agent interfaces operate the same saved project and original workspace lease. An operator can begin with a browser review, continue through the command line or MCP tools, then export and reopen the same complete project. This makes the deliverable useful for a small publisher operating its own catalogue and for a partner who commissions an implementation and transfers responsibility to customer staff.

### Following editions and retained publisher history

The [recurring catalogue procedure](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/58ce16a5eca080b6f082d2db884ac55f34f67cc3/stellar/scf-starforge-20261009/sf30-seller-sdk/ckan/RECURRING_CATALOGS.md) extends the same project to a publisher's current HTTPS document. The operator saves the original publication URL, declared or automatically detected profile, private token environment reference when needed, request limits and a due-check interval. Each changed configuration becomes a retained version, and the selection history records subsequent choices between versions.

An acquisition retains the actual request and redirect history, response status, relevant cache and retry headers, exact response bytes, byte count and completeness. A bounded partial response remains inspectable as a partial response. Public conditional requests can reuse a saved edition only when its original binding and retained bytes still match. Sources using a private token reference receive complete entities, and credentials stay in the host's private environment. Publisher retry deadlines remain effective across configuration changes and redirects.

The operator then selects the latest acquired document and an explicit accepted predecessor release. The comparison binds that release's candidate and review hashes. Any accepted identity decisions to carry forward are selected individually from the predecessor's complete report. With an automatic candidate, those decisions resolve against the newly converted current source while its other fields remain fresh. With an explicitly uploaded corrected candidate, its bytes remain unchanged and the selected decisions are resolved against the current source and candidate using their typed identifiers, catalogue scope and record role. Missing, ambiguous or overlapping selections become a preparation finding requiring an explicit correction.

This produces a repeatable service: acquire a following publisher edition, inspect its source and changes, resolve the selected decisions, prepare a review and release the chosen candidate through the existing operation. Acquisition alone leaves the current accepted release intact. Failed and interrupted attempts remain in history, and an explicit retry links to the original attempt.

The installed due-check command uses the host's existing scheduler. While the application is open, it verifies the original private startup record and dispatches through the running workspace owner. When the workspace is closed, it obtains the existing lease. Busy workspaces defer to the next scheduled invocation, and both the saved interval and publisher retry deadline remain effective. This preserves one operation owner across interactive and recurring work.

Source versions, acquisition receipts and bodies, complete reviews, typed mapping decisions and release history travel in the original whole-workspace archive. The receiving operator supplies the destination's private environment, reopens the saved project and continues from the retained latest-edition identity.

The [complete recurring customer programme](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/58ce16a5eca080b6f082d2db884ac55f34f67cc3/operations/dcat-recurring-catalog-390e-20261013/README.md) joins the original domain operation to the existing browser and archive receiver in one process. The receiving phase uses that post-review archive and its exact hash. A separately opened application then inspects the received history and complete state.

The programme keeps the domain operation, browser operation and received-project reopening as separate results under one customer operation. Its final outcome is complete only when all three actual phases complete. The source and operating guide are shipped; the next native execution will produce the retained interface and receiving artifacts for that selected installation. The original standalone source edition remains identified, so a later application edition can be compared explicitly rather than silently replacing the programme being received.

For a customer's deployment, the implementation partner selects one actual catalogue, the destination environment, the required output and the person responsible for acceptance. The operator delivers the reviewed candidate plus the complete editable project, runs the customer's export or publication procedure, and records the selected candidate and deployment context. Subsequent editions reuse the saved operating procedure and the customer's original acceptance responsibilities.


### Semantic profiles that a customer can inspect and receive

The [semantic catalogue workflow](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/5a8c6cb8d1b539cbb53d601540fae9c861b4f251/stellar/scf-starforge-20261009/sf30-seller-sdk/ckan/SEMANTIC_CATALOGS.md) adds an explicit interpretation and conformance review to the same retained catalogue project. An operator imports the complete local JSON-LD context, original SHACL shape files, any selected ontologies and supporting audit material as an immutable profile. The profile records its intended base IRI, context treatment, inference settings and original file identities. Updating it creates a following profile; earlier attempts retain their original selection.

This is useful when a customer needs to know whether the catalogue can be consumed under a particular vocabulary or contract. The operator selects an exact original catalogue or reviewed candidate and runs the unchanged native RDFLib/pySHACL engine. The retained result includes the derived document, graph and provenance, class-presence measurements, full validation findings, original jobs and native artifacts. Source bytes remain available separately from their selected semantic interpretation.

The context treatment is an operator decision. A legacy catalogue carrying a remote root context can be reviewed with an explicitly selected local replacement; a current catalogue without a root context can require its absence before the retained context is applied. The base IRI determines how relative identifiers are interpreted. Neither setting is silently inferred from a prospective customer outcome. Optional published profiles retain their own audits and limitations so that the customer can assess what their vocabulary actually describes.

The operating distinction is material to a commercial service. JSON Schema validation describes the source document's structural validity. Record conservation describes whether migration retained its members. Native SHACL conformance describes the graph under the selected shapes and parameters. Class counts describe observed class presence; they do not establish complete coverage of every SHACL target. A conforming result can still have little or no relevant target coverage. The complete review keeps those facts separate from the customer's catalogue acceptance and deployment decision.

A reviewer can page through complete findings with their original focus nodes, paths, values, severities, messages and nested details, then download the full original report and artifacts. An unavailable or oversized interactive result is identified explicitly and retains its complete-file route. A decision records the exact run and preceding decision identity; it cannot overwrite a later review silently. An acknowledgement of a failed or interrupted attempt preserves what happened without claiming conformance. These controls make the result explainable to a customer and reusable by another operator.

### Explain graph changes and the scope of relationship impact

The [saved snapshot comparison workflow](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/212a85843d89f166d66f46f9dd934bd610c57cbf/stellar/scf-starforge-20261009/sf30-seller-sdk/ckan/SEMANTIC_COMPARISONS.md) answers a different customer question: what changed between two retained interpretations, and which relationships were examined because of that change? The operator selects the ordered before and after runs, binding the exact catalogues or candidates, profiles, base IRIs, completed graphs and original provenance. A completed snapshot can remain useful even if a later validation phase failed.

The original engine calculates the complete added and removed RDF statements and handles graph equivalence and blank nodes. Relationship impact is a separately selected traversal with explicit predicates, depth and visited-node limit. The report retains complete graph difference separately from limited impact. When the traversal reaches its cap, the known lower bound and truncation remain visible; the operator cannot describe the observed subset as a complete downstream inventory.

The complete changes, visited nodes and traversed relationships remain available as original typed rows and downloadable files. Each side's profile and base are part of the interpretation: if those differ, the reviewer describes that fact rather than attributing every graph difference to the publisher's catalogue update. Selecting the same snapshot twice is also a meaningful unchanged-source comparison. The resulting decision records the exact comparison, selected scope and review chain, while the existing catalogue release remains an independent decision.

For an implementation partner, this supports a useful following-edition service. A customer can receive the original acquisition and migration review, the vocabulary-specific findings, and an explanation of the retained graph changes with the actual impact scope. The partner can then agree the particular corrections or downstream integration work to perform. The service does not promise that a bounded relationship traversal discovered every affected external system.

### Turn retained evidence into editable operator delivery work

The [LDA catalogue handover procedure](https://github.com/woahwhattheheck/LocalDeviceAgent/blob/99fae766a334d4a613c921b79e9e32d07450d1bf/tools/phone_driver/DCAT_HANDOVERS.md) connects the delivered catalogue material to the existing File Collections, Documents, Search, Work Briefs and Action Plans. It receives the original Merchant whole-workspace archive as a declared semantic source. The original archive stays intact in the Collection. The operator can navigate profiles, validation runs, findings, comparisons, graph changes, nodes, relationships, artifacts and decisions through their original identities. Opening a finding or changed statement explains its original profile/run or comparison and the archive member from which it came. This makes it possible to deliver a customer's working explanation along with the technical output. The operator saves a handover edition with review notes and an ordered selection of the original records that explain the task. A Brief resolves those selections through the existing source reader and freezes the exact references and hashes used in the saved document. A large original file remains available as a full download; an appropriately selected complete finding or decision can support the Brief without silently shortening the underlying evidence.

The existing Action Plan writer then uses the exact saved Brief edition. Each finite task names the concrete work, supporting Brief sources and an observable completion condition. For example, a customer may need to inspect an identified vocabulary mismatch, choose an explicit context/profile interpretation, correct a catalogue record, integrate the chosen candidate into an actual publication route and receive the resulting operator procedure. The task selection follows the customer's original source and requirements. Saving the plan does not execute those tasks, alter an upstream result or turn a technical acknowledgement into a release decision.

The complete editable package carries the original Collection and semantic archive, selected handover edition and retained history, and its linked original Brief and Action Plan packages. The recipient receives its own local Collection and handover identities while the source file identities, sender origin and original evidence remain attached. Included Briefs and Plans retain their current saved editions and full original histories through their existing portable receivers. The receiving operator can inspect the same original member, edit local delivery notes, reopen the linked work and export a following package without modifying the sender's project.
