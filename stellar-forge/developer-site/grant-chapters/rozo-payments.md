## ROZO payment operations, financial closing and complete receiving

ROZO payment operations connects the merchant’s original provider requests, retained observations and reconciliation reports to the configured Accounting and Buyer applications. Staff can carry a selected report through recognition, source review, exact allocations, dated period closing, accountant review and complete project receiving. The original request, report edition and financial decisions remain linked when another operator takes over the installation.

This is an implemented product contribution to the existing Stellar merchant workspace. It supplies reusable customer commissioning and financial receiving software for the same prospective integrations described in the application. The current source selection is the merged configured-finance release, PR1064 at a480c70a6cb4b5dfa89976d2978013af9b70794e. Native installation and full customer receiving continue through the original ROZO commissioning operation; its returned completion records establish the operated edition.

### Commission the original merchant installation

The commissioning workorder selects the actual merchant, provider connection, receiving engineer, source context, retained ROZO workspace, existing merchant configuration and its Accounting/Buyer aliases. It names the person responsible for source acceptance, period decisions, accountant review, backup and receiving. The [maintained installation guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/a480c70a6cb4b5dfa89976d2978013af9b70794e/stellar/scf-starforge-20261009/distribution/selections/ROZO_PAYMENTS.md) and [complete runtime selection](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/a480c70a6cb4b5dfa89976d2978013af9b70794e/stellar/scf-starforge-20261009/distribution/selections/rozo-payments.json) build the original product together with its schema and MCP dependencies. Applications reviews, saves, starts and opens that same selected installation.

The [Applications provider](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/a480c70a6cb4b5dfa89976d2978013af9b70794e/stellar/scf-starforge-20261009/sf30-seller-sdk/rozo-payments/application-provider.mjs) binds the original workspace and connection configuration, including the selected merchant configuration and any separate Buyer connection file. Host-local environment references supply provider credentials and the existing encrypted-backup passphrase. Staff use the original provider mode and declared source context throughout the operation. A received active workspace continues its own identity, requests and history.

### Operate the payment and report before its financial close

The merchant creates and tracks its original provider request, retains complete callback and polling observations, reconciles incoming payment, fee and destination evidence, and saves the selected period report. A report is selected by its identifier, version and complete original SHA-256. The source retains that report’s JSON, CSV/HTML presentation and original payment objects, so a later renderer or following observation does not replace an earlier captured edition.

The [original financial source reader](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/a480c70a6cb4b5dfa89976d2978013af9b70794e/stellar/scf-starforge-20261009/sf30-seller-sdk/rozo-payments/finance-source.mjs) preserves three independently typed movements: source payment, source fee and destination payout. Each keeps its native units, original chain/network, token address, symbol and decimal precision. Provider confirmation retains its provider provenance. An expected, absent, unsettled or unresolved amount remains visible for review. Commercial valuation, account recognition and Buyer ownership are explicit later decisions.

| Operating stage | Staff decision | Complete retained result |

### Carry the report into the configured financial owners

The [financial service](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/a480c70a6cb4b5dfa89976d2978013af9b70794e/stellar/scf-starforge-20261009/sf30-seller-sdk/rozo-payments/finance-service.mjs) uses the original configured Accounting and Buyer owners, their native workspace locks, revisions, requests and maintenance lifecycle. The ROZO Finance interface has Intake, Merchant, Buyer, Accountant and Deliveries views. Its [complete staff workflow](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/a480c70a6cb4b5dfa89976d2978013af9b70794e/stellar/scf-starforge-20261009/sf30-seller-sdk/rozo-payments/public/finance.mjs) saves the exact original request before dispatch and can reconcile that same accepted operation after a lost response.

Merchant recognition begins with an explicit accounting date, reviewed movement basis, evidence acknowledgement and complete allocation lines. Every line retains amount, account code, cost centre, project and memo. The operator inspects actual period exceptions, including stale source/coding, unresolved evidence and previously closed movements. A period review binds its original context; its close preserves that reviewed source. The [configured merchant tools](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/a480c70a6cb4b5dfa89976d2978013af9b70794e/stellar-forge/mcp-merchant-operator/ACCOUNTING_ROZO.md) expose the same intake, coding, period, accountant, original-file and request-recovery operations to the existing MCP client.

Buyer participation requires a separate explicit purchase selection. Each selected source payment retains its exact movement ID and basis, actual purchase owner, purchase reference and reason. Staff can intentionally receive the report as reference-only with an empty purchase list. The [original Buyer provider](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/a480c70a6cb4b5dfa89976d2978013af9b70794e/stellar-forge/mcp-merchant-operator/BUYER_ROZO.md) carries selected purchases through its native source review, cost centres, complete asset labels, coding, permitted issue dispositions and period close. Fees and destination payouts keep their own merchant meaning.

Earlier accepted source, coding and close history remains available during corrections. The current native models retain the original reopen and following-close operations. A later source edition is reviewed against that original history; new coding and a following close keep their own decisions and relationship to the earlier close.

### Give the accountant complete work and receive the actual return

Each accountant handoff is created from its exact issued close and original source hash. Merchant and Buyer handoffs retain their distinct typed source. Staff download the whole original file set and give the accountant the editable CSV together with its retained source. On return, the operator previews protected-row differences and applies that exact preview against the actual parent revision. Subsequent returns identify their preceding return.

Financial review is recorded as REVIEWED when the programme performs evidence review. Any separately received external posting status keeps its own actual source. The Deliveries view retains original issued files, the complete financial source and full Buyer project. Native file readers preserve the original filename separately from the safe download filename and verify all received bytes against their saved identities.

The [complete operating guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/a480c70a6cb4b5dfa89976d2978013af9b70794e/stellar/scf-starforge-20261009/sf30-seller-sdk/rozo-payments/FINANCE.md) begins with a read-only finance plan generated from the actual saved report and configured workspaces. The resulting complete archive includes original ROZO source/evidence, all Accounting operating files in their encrypted backup, the full Buyer application/database/source project, original and returned accountant files, selected plans, original requests, native results and receiving records. The [archive receiver](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/a480c70a6cb4b5dfa89976d2978013af9b70794e/stellar/scf-starforge-20261009/sf30-seller-sdk/rozo-payments/finance-archive.py) verifies every declared member before application execution. An interrupted run retains its plan, accepted requests, process attempts and actual maintenance jobs. Packaging continues from the completed native result and original files.
