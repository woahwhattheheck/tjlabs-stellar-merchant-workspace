# Forecast financing and whole operating decisions

## Forecast financing options, protected customer funds and Planning limits

The existing Grant Operations application now supports a complete financing decision: retain alternative delivery and payment assumptions, calculate them against the same original operating-case version, compare their cash and capacity requirements, state explicit planning limits, and deliberately adopt one complete input into the original Forecast workflow. The result remains editable and can be exported with its original sources, comparison history, decisions and unfinished work for another authorized operator.

This is part of the same six-package, 400-hour, USD38,000, 150-day SCF program. It does not add funded hours, change the issuer's acceptance criteria, turn a proposed customer workshare into a sale, or count a planning comparison as a purchase or delivered result. The previously retained financing analysis and its historical source selections remain available. Actual grant receipts, commercial agreements, bank cash and acceptance evidence continue to be recorded in their original case workflows.

### The complete operator decision

A facilitator opens the actual operating case and its Forecast view. Each named financing option captures the complete current input, its source context and the operator's note. Partly entered amounts and dates remain unfinished work; capturing a draft does not make it calculable. Replacing an option preserves its prior name, note and full input rather than overwriting the original assumption. The study also retains archived options and earlier comparisons.

Calculation submits one to24 active options to the original Forecast calculator under one locked case/source version. Each result carries the complete native preview, input hash and common request/source identity. If any option is invalid, the batch reports that original option's native error; it does not silently compare a successful subset. A changed case version is rejected before calculation, and the operator can retain the earlier comparison while preparing a fresh one against the actual current case.

The comparison includes each option's original daily cash curve, grant and commercial assumptions, remaining effort, workload, invoices, findings and valuation coverage. It has explicit controls to inspect complete rows and download the full results. Conditional expected income remains conditional. Existing cash or an invoice allocation is not evidence that a customer's entire payment remains unspent.

### Customer delivery obligations remain protected

The original customer-funding calculation distinguishes pooled cash from amounts reserved for remaining modeled customer delivery. Opening attribution requires an explicit operator-entered amount with its reconciliation basis and retained source references. Gross observed customer receipts are not automatically copied into an unspent opening balance.

For an included customer, the reservation is the smaller of its positive attributed balance and remaining modeled delivery obligation. Original included invoice liabilities are counted once; the workbench does not add all gross invoices or all historic delivery costs again. An exactly zero remaining obligation needs no reservation, even when its opening attribution is unknown. Unknown future costs, cash valuation or bank opening remain visible and cannot create a numeric available balance or funding gap. These reservations are planning restrictions, not assertions that a bank or contract legally ring-fences the money.

The operator can compare original grant-only requirements, combined cash, or the customer-protected funding measure. The report distinguishes maximum required starting cash from extra funding after a known total opening balance. Disabling protection retains its input for later review without treating a disabled result as a known zero.

### Explicit limits and a conditional shortlist

Planning limits accepts the actual selected cash measure and amount, peak weekly-equivalent effort and overloaded-day tolerance. Blank and zero have different meanings. Raw partial criteria survive working-file recovery; an incomplete criterion cannot produce a finished assessment.

Every option receives an explicit **meets entered limits**, **exceeds**, or **unresolved** result, with the original value, date, basis and reason. A known dated overload can exceed a limit even when other work is undated. Positive selected undated work prevents an otherwise passing capacity result. Unknown or unvalued undated delivery obligations prevent combined cash from passing. A protected-cash result requires that original calculation to be enabled and sufficiently valued.

The finite shortlist only compares fully known, passing options with the same original work scope, source horizon, capacity basis and liability coverage. Included and excluded unpaid invoices belong to different scopes; omitting a liability cannot make an option appear to dominate one that funds it. Exact cents and the retained native capacity values are compared without introducing rounded display values into the decision. Equal options remain visible. The shortlist is conditional on the finite entered alternatives, not a claim of a global optimum or permission to commit expenditure.

Each assessment retains its criteria, note, complete result and selected native comparison. Reusing earlier criteria preserves displaced unfinished criteria. Historical results stay readable when every option has been archived. Decision-linked adoption must contain the exact calculated option input and original source version; malformed portable histories cannot attach a different funding amount to an earlier favorable assessment.

### Deliberate adoption, original save and whole receiving

Adoption shows the before and after inputs and leaves the decision with the operator. It goes through the original Forecast draft, native Preview and Save. It does not write cash, issue invoices, accept customer terms or create an award. Concurrent editor or case changes are checked before replacement. Rejected source or preview operations preserve the current draft.

The complete study can be retained as a source in the same case. The original source request is durably recorded before dispatch, and an accepted receipt is retained before refresh. An uncertain reply resumes that exact request rather than creating another attachment. Full working files include raw unfinished values, source attachments, original comparisons, criteria, assessments and adoption history. Recovery downloads remain possible when local persistence fails. Native case export and application handover preserve the original plan, forecasts, financial events and every source edition.

A received native case may have a new local case ID. The workflow verifies its actual original ancestry and source context; it does not rebind an arbitrary file by matching a label. A following calculation uses the received case's current version before a new adoption. Previous results keep their original case/source identity.

The original file hash is checked before transport. The adapter calls the same typed native method and retains the entire native result in its existing snapshot/rows/file interface. This closes a concrete reachability gap: having the new native client on disk previously did not make the comparison available through the provider's strict tool catalog.

The original Grant Operations recipe selects the complete SF47 component and managed execution inventory. The installed package therefore carries Python calculation and routes, client declarations, browser modules, styles, guides and recovery dependencies together. Its original builder also follows selected Node/browser imports and rejects missing managed files. A description-only recipe correction restores compatibility with the existing1,024-character validator; no command, component, export, support file, dependency or earlier feature is removed.

The release is built from one immutable source commit with the existing `build.mjs --selection grant-operations`, then prepared, installed and inspected through `runtime-install-cli.mjs`. An upgrade uses a separate runtime and retains the earlier installation. Applications reviews the actual runtime, private workspace, scenario, Python executable and full source-selection hash before saving and starting the original listener. An accepted running application is not changed by copying individual files into it. The headless operator must not compete with a running service's workspace lock; browser, typed-client and Merchant use the original authenticated listener.
