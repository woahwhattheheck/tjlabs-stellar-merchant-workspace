# Recovery commissioning and complete customer receiving

This chapter supplies the operating procedure and source selection for the grant's existing monitoring, recovery and maintainer handover work. The canonical application selects it under the H2 **Recovery commissioning and complete customer receiving**. It adds no package, budget, purchase target or submission decision.

## Recovery commissioning and complete customer receiving

A customer needs to continue the original useful task after a host, source process or delivery path fails. Restoring the customer's output alone can leave the application without its request, configuration, entitlement, incident or notification history. The maintained recovery product preserves the complete selected state and gives the next operator an explicit review, authenticated receiving procedure and supported continuation. The recovery selection depends on what the customer actually owns: a managed buyer workspace, an eligible standalone free Object session, or the retained incident store. Each retains its own native engine and authority.

### Select the complete operating state

The installation engineer and receiving maintainer first identify the original application edition, state root, session or workspace identity, complete output locations and actual source dependencies. They record the private backup destination, encryption custody where applicable, current writer owner, destination filesystem requirements and who may authorize a continuation. The selected state includes the original operation history; a delivery report is useful evidence but does not substitute for missing session or ledger files.

| Selected operating source | Complete retained unit | Receiving boundary |
| --- | --- | --- |
| Managed buyer workspace | Original buyer state, approved requests, operator keys and native financial journals through the existing managed recovery workflow | The managed engine authenticates its original selection and reopens the same workspace; financial reconciliation stays with the original intent. |
| Standalone free Object session | Native definition, configurations, inbox attempts, evidence, response chunks, recorded assemblies, signer/policy dependencies and prior lease history | The standalone engine requires the actual eligible zero-cap session and an explicitly absent configured ledger; restore uses its original canonical state root. |
| Incident and Support operation | Exact incident-store configuration and revision, retained observations, incident and acknowledgment history, notification attempts/receipts, referenced captures and earlier receiving provenance | The incident receiver publishes a separate store with notification delivery held, then the existing Support console opens that received source and case. |

The [standalone operating guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/f326d6567ca670e82c098119155ed9e2c994299e/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/OBJECT_SESSION_RECOVERY.md) defines the exact eligibility and complete source selection. Its [original shared recovery engine](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/f326d6567ca670e82c098119155ed9e2c994299e/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/workspace-recovery.mjs) keeps the existing managed path and standalone path in the same maintained implementation. A session with nonzero spending caps or an existing configured ledger requires its corresponding managed recovery selection; the standalone interface does not manufacture a missing financial history.

If only an earlier analytical export survives, receive its original data through the supported native Object API and retain the actual resulting session identity and lineage. That is a data-receiving operation with its own observed outcome. It must not be described as recovery of unavailable original session metadata. The complete subsequent backup then preserves the session that actually exists.

### Review and capture the original Object session

The trusted host configuration declares the permitted source, complete state root, included dependencies, fixed encrypted bundle and actual session ID. An operator selects those declarations in the existing SF101 workspace. The browser and agent tools do not select arbitrary filesystem paths or provide a passphrase. The host's established secret facility supplies the value named by the profile's passphrase environment reference.

The operator inspects the current source and saves its complete native review. Before snapshot, the responsible source owner stops writers through their normal application control and acknowledges quiescence. The backup acquires the original Object BACKUP lease, checks the reviewed state again, captures every selected member and validates the source before and after copying. Earlier lease records remain part of the original state; the new sealed backup claim is retained separately. Source change requires a fresh explicit review.

The receiver keeps the encrypted bundle and its exact returned record digest. Independent verification authenticates the record, every selected member, the native definition, chunk configurations, recorded assemblies and sealed backup lease. The native command checks the absent ledger fact in the captured standalone state. Verification supplies evidence about that backup; it performs no acquisition or financial action.

The [typed native SDK](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/29d6f97c8411360afd66d8ba8a55a35896fa9bcb/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/node/workspace-recovery.mjs) returns the complete native result together with process and cleanup facts. A published result can coexist with a failed post-publication check. The operator retains both before deciding what remains to be repaired.

### Restore, reopen and continue through the existing workspace

On the receiving host, the selected original canonical root must meet the native engine's absent or empty private-directory requirements. The application/runtime is installed separately from the state backup. Restore authenticates the same complete record and publishes the whole state before reopening its native checkpoint. The command does not start an acquisition, sign, finalize or make a payment.

The restored root has a marker for that exact backup. Repeating the same restore after a lost reply reopens its current state and preserves later native work. A different backup or an unrelated populated root is a conflict. The operating procedure resolves that actual selection instead of deleting live state to make restoration succeed.

The [SF101 workspace guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/29d6f97c8411360afd66d8ba8a55a35896fa9bcb/stellar/scf-starforge-20261009/sf101-merchant-recovery/workspace/OBJECT_SESSIONS.md) describes the complete browser, CLI and MCP operation:

1. Select the original declared session, inspect it and review the chosen action.
2. Confirm the exact saved review; for capture, acknowledge that its writers are stopped.
3. Start the request once. The existing workspace saves its original request before native dispatch and retains complete native evidence before reporting its outcome.
4. After a lost response, read that request. Repeating Start reads an existing Object request; it does not silently resume it.
5. Explicit continuation selects the saved review hash and the attempt just observed. Snapshot continuation also requires fresh quiescence acknowledgment. An older attempt selection returns the newer retained record without another dispatch.
6. Verify the selected backup, review its original destination and perform restore or same-backup reopen. Inspect current native state separately from the earlier saved request outcome.

The [complete workspace adapter](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/29d6f97c8411360afd66d8ba8a55a35896fa9bcb/stellar/scf-starforge-20261009/sf101-merchant-recovery/workspace/object-sessions.mjs) delegates to the original SDK. It saves complete content-addressed native evidence, including failed outcomes, while the existing workspace owns the request queue, writer lease, cancellation and shutdown. Closing the host aborts and drains its owned work before releasing that lease. Keep the complete workspace, saved reviews, evidence, host declaration, bundle and original data lineage in the customer's receiving set. Passphrase custody remains separate.

### Receive incidents without replaying notifications

A source incident store can remain live while its complete snapshot is copied. Under the original short transaction lease, snapshot pins the reviewed raw state and all native capture references. Ordinary capture collection honors those pins while the watcher advances. An interrupted copy resumes that frozen selection. An unwanted incomplete snapshot is released only through its explicit abandonment operation with the original pin and operator reason.

The complete inspector checks the exact manifest, all required file hashes and sizes, native state and capture parsing, and retained provenance. Receiving verifies those files before publishing an operative store. A completed receiving operation reopens the current received store rather than replacing later live changes. The [incident recovery guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/29d6f97c8411360afd66d8ba8a55a35896fa9bcb/stellar/scf-starforge-20261009/sf93-seller-support-bundle/INCIDENT_RECOVERY.md) supplies the full snapshot, inspect, receive, abandonment and Support procedures.

Notification identity remains part of this state. The receiving copy retains original events, bodies, destination bindings, attempts, provider receipts and deadlines. Terminal events retain their outcome. Unfinished events are individually paused, and the received store starts with a global delivery hold. Opening it in Support starts no watcher and sends no notification.

To release that hold, the responsible operator stops the original writer, reviews the actual received queue and retained receipts, and selects the exact recovery, manifest, queue and configuration digests. Original attempt deadlines still apply. Reconciliation records that review and releases the global hold; it does not automatically retry individually paused events. Any later retry selects the original event through the existing destination and attempt checks. A lost webhook acknowledgment remains an at-least-once delivery uncertainty and requires the original receiver's deduplication.

The [saved Object observation and Support workflow](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/29d6f97c8411360afd66d8ba8a55a35896fa9bcb/stellar/scf-starforge-20261009/sf93-seller-support-bundle/OBJECT_MONITORING.md) binds a complete native read to the selected session/configuration and original bytes. Incomplete, stale or repeated evidence cannot count as a fresh healthy recovery. Configuration replacement retains retirement separately from recovery. The same Support case carries the original observations, acknowledgment, generated report, handoff and independent reopen.

### Demonstrated operation and current implementation

The completed standalone native operation on 13 October 2026 inspected the retained session, created its encrypted snapshot, independently verified it, restored its canonical state, made a later native assembly and reopened the same backup. The original 267-byte data and session/configuration identity remained intact. Assembly count increased from one to two; reopening preserved all 32 current state files and 27,430 bytes. The original 291,120-byte source archive remained unchanged. The source remained NO_PAYMENT_REQUIRED with no ledger and no new HTTP or payment operation. This actual outcome is recorded with [merged standalone recovery PR787](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/pull/787).

The original Support customer operation also completed whole incident-store snapshot, inspection, receiving, Open, reviewed case preparation, recovery reconciliation, complete case export and independent native handoff reopening. Its saved snapshot and received store were continued through the actual current incident revision and fresh native access binding, retaining the earlier rejected request. The selected exercise had no notification entries and sent none; it does not claim a delivered-notification restore exercise. All original Object bytes remained unchanged. The complete recovery delivery contains 904 members and 9,185,119 bytes, as recorded with [merged original continuation PR727](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/pull/727).

The native engine therefore has an operated recovery history. The later MCP caller and complete SF101 browser/CLI/client integration are merged source, independently reviewed against that engine. Their selected native caller execution remains pending. The browser's connected source checks establish its confirmation and same-request behavior at that source boundary; they do not establish a full installed browser/native customer result. These states remain separate in the receiving record.

### Apply recovery to the existing funded installations

T1 establishes each customer's actual source, authority, output definition, state custody and named operational/receiving owners. T2 applies monitoring and same-case incident response to those selected hosts, including original notification and financial uncertainty. T3 performs the customer's off-host recovery and maintainer handover, then observes continued useful service. Completed component development is the starting point for those installations; this chapter preserves the existing six packages and their current acceptance and payment clocks.

The receiving engineer records the actual selected source and backup, original operation identity, authentication result, restore/publication and reopen diagnostics, retained financial/output history, later-state preservation and customer decision. Measure elapsed recovery time, active engineering effort, unresolved dependencies and time to useful continued output separately. A complete free-data recovery is a recovery outcome. Paid adoption still requires the application's original independently observed settlement and useful-output criteria.

Commissioning is complete when the receiving maintainer can inspect the full selection, authenticate and receive it through the maintained engine, reopen the same incident or customer task, and perform its next authorized useful step with original history intact. Residual findings, pending notification reconciliation, missing external dependencies and unexecuted caller surfaces remain visible in that same operating handover.
