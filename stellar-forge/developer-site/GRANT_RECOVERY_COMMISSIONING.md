This chapter supplies the operating procedure and source selection for the grant's existing monitoring, recovery and maintainer handover work. The canonical application selects it under the H2 **Recovery commissioning and complete customer receiving**. It adds no package, budget, purchase target or submission decision.

## Recovery commissioning and complete customer receiving

A customer needs to continue the original useful task after a host, source process or delivery path fails. Restoring the customer's output alone can leave the application without its request, configuration, entitlement, incident or notification history. The maintained recovery product preserves the complete selected state and gives the next operator an explicit review, authenticated receiving procedure and supported continuation. The recovery selection depends on what the customer actually owns: a managed buyer workspace, an eligible standalone free Object session, or the retained incident store. Each retains its own native engine and authority.

### Continue an interrupted cold-host adoption through the same reviewed operation

The existing public host handoff now supports an explicit receiving operation. This completes the interruption path after the original encrypted bundle has been authenticated and restored for review. Previously, the direct exclusive copy could leave a partial canonical receiving root that the next call correctly refused to merge. The maintained command can now retain the reviewed selection before copying, resume its own private partial staging and publish each complete root without replacing an existing destination.

The receiving review binds the original bundle and staging paths, manifest and plan digests, workspace identity, original mappings and request history, target bytes, external receiving-file fingerprints, operation directory and selected publication executable. Reuse that exact operation and review to continue after an interruption. Source authentication remains with the existing snapshot engine. Original Object sessions, configurations, request attempts, Support cases, comparative evidence, encrypted attachments and later source editions stay in the complete captured roots; this continuation does not create replacement customer state.

A whole root remains private until its complete inventory has been copied and checked. Files resume only from a matching prefix. Publication uses Linux no-replace rename, so a concurrently created destination cannot be overwritten. Existing exact roots are fully checked and reused, including a root whose publication finished before the caller received its acknowledgment. The original SF98 receiving lease covers copy, publication, final mode restoration, full receiving validation, read-only native workspace reopening and immutable completion. Its inherited descriptor keeps the same lease held while the original publication child is still working.

The first successful result retains its original completion time and saved workspace state. The operator can read that recorded result separately after a lost reply. Such a read does not assert that today's host is unchanged. Repeating adoption performs the original current inventory, absent-input, external binding and read-only reopening checks again; later work is preserved rather than overwritten to reproduce an earlier result. The invocation without an operation directory keeps its existing behavior, and an older partial root without recorded staging custody is not silently claimed by the new operation.

The complete operator guide carries review, adoption and recorded-status commands, the Linux/Python and existing flock requirements, exact source selection and interruption behavior. No dependency installation, service launch, provider request, payment, restore of a standalone Object backup or replay of an original customer request is introduced by this receiving continuation.

The trusted host configuration declares the permitted source, complete state root, included dependencies, fixed encrypted bundle and actual session ID. An operator selects those declarations in the existing SF101 workspace. The browser and agent tools do not select arbitrary filesystem paths or provide a passphrase. The receiver keeps the encrypted bundle and its exact returned record digest. Independent verification authenticates the record, every selected member, the native definition, chunk configurations, recorded assemblies and sealed backup lease. The native command checks the absent ledger fact in the captured standalone state. Verification supplies evidence about that backup; it performs no acquisition or financial action.

### Restore, reopen and continue through the existing workspace

On the receiving host, the selected original canonical root must meet the native engine's absent or empty private-directory requirements. The application/runtime is installed separately from the state backup. Restore authenticates the same complete record and publishes the whole state before reopening its native checkpoint. The command does not start an acquisition, sign, finalize or make a payment.

The restored root has a marker for that exact backup. Repeating the same restore after a lost reply reopens its current state and preserves later native work. A different backup or an unrelated populated root is a conflict. The operating procedure resolves that actual selection instead of deleting live state to make restoration succeed.

The [SF101 workspace guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/29d6f97c8411360afd66d8ba8a55a35896fa9bcb/stellar/scf-starforge-20261009/sf101-merchant-recovery/workspace/OBJECT_SESSIONS.md) describes the complete browser, CLI and MCP operation:

1. Select the original declared session, inspect it and review the chosen action.
2. Confirm the exact saved review; for capture, acknowledge that its writers are stopped.
3. Start the request once. The existing workspace saves its original request before native dispatch and retains complete native evidence before reporting its outcome.
4. After a lost response, read that request. Repeating Start reads an existing Object request; it does not silently resume it.
5. Explicit continuation selects the saved review hash and the attempt just observed. Snapshot continuation also requires fresh quiescence acknowledgment. An older attempt selection returns the newer retained record without another dispatch.
6. Verify the selected backup, review its original destination and perform restore or same-backup reopen. Inspect current native state separately from the earlier saved request outcome.

### Compare complete backup editions before selecting a restore

Maintenance can change a customer's configuration, checkpoint, downloaded chunks or assembled outputs between backups. The [complete comparison operator](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/134640608b6fe4b53b5a2268b02d26207e320f0d/stellar/scf-starforge-20261009/sf101-merchant-recovery/workspace/OBJECT_COMPARISON.md) lets the receiving maintainer authenticate both selected originals and review those differences before choosing a separate restore. It extends the same recovery workspace and request queue used above.

The trusted host declares two existing encrypted backup locations for the same actual Object session ID, canonical session directory and state root. The operator selects both declarations and both exact record digests. A changed configuration or native definition remains a reported difference; a different source session or canonical root is rejected. Browser and agent selections contain declaration IDs and record identities. Secret values, filesystem paths and passphrase environment choices remain in trusted host configuration.

The workflow is complete through the existing browser, attached CLI and typed merchant client:

1. Select the before and after editions and retain their original order. Review both exact digests under one stable request ID.
2. Confirm that saved review and start authentication. The original queue stores the request before dispatch. The native engine verifies each complete encrypted backup, including every selected member, before the comparison can report both sides authenticated.
3. Read changes in full member and source inventories, configuration, checkpoint and recorded session history. Added, removed, changed and unchanged members remain distinguishable; the payload retains both complete original records and a full union that indexes those records.
4. Download the complete native JSON and readable HTML or Markdown report, bound to their exact byte counts and SHA-256. The report retains both verification results and the original comparison identity.
5. After a lost reply, reopen the original request. An unfinished operation requires explicit continuation with its saved review hash and observed attempt; a repeated start does not silently create another attempt. Reopening a saved report reads that recorded result rather than asserting a new authentication of today's files.

The [native comparison core](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/134640608b6fe4b53b5a2268b02d26207e320f0d/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/object-comparison-core.mjs) reports chronological context and complete JSON-pointer changes in non-file original record fields. Its pure record comparison makes no authentication claim. Authenticated native comparison requires both complete native verifications and the same-source checks. If one side fails, the saved partial result identifies the failed side and retains any already completed authenticated side; it is not presented as a completed pair. Process, cancellation, cleanup and report-publication failures remain visible even when some output has already been retained.

The [workspace adapter](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/134640608b6fe4b53b5a2268b02d26207e320f0d/stellar/scf-starforge-20261009/sf101-merchant-recovery/workspace/object-comparisons.mjs) saves complete SDK results and immutable readable artifacts. Its reports do not carry ciphertext: both original encrypted bundles, or their complete portable transfer archives, remain separate receiving inputs, with passphrases held separately.

Comparison itself performs no restore, acquisition or payment. A maintainer can use its findings to select an edition, then use the existing original `object-restore` review and canonical destination checks.
