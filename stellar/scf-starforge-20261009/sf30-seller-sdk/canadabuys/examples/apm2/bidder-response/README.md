## Complete receiving and interruption recovery

operate.mjs saves each complete mutation intent before requesting the native write. Its command ID, input and expected revision remain unchanged after response loss; the original bidder API returns the existing committed result. Each completed edition is read back by its saved revision and digest.

The working JSON and readable artifacts use private exclusive temporary files, fsync and atomic replacement. A retained master is hash-checked before continuation. The source edition and both workspace IDs must match the original operation. After records and review are saved, HTML/JSON/CSV decision reports, complete master/annexes and a selected source/record package are retained.

Before receiving, the entire original workshare and its complete history are bound in bound-workshare.json. The retained exported package is checked against every saved record head, every frozen decision-context edition, the original source entry and the bound full workshare. New or changed selected documents/requirements are reported in export-review.json. A second native context comparison after retaining the exported bytes is saved as export-context-comparison.json; it detects a newer current source/profile selected during export before the original receiving starts. A differing complete package remains saved for review in the existing desk.

Receiving uses the original saved package ID and original receiver. Its receipt is reconciled before mutation. Every received bidder edition is read back; each captured evidence body is downloaded and checked against its native byte/hash identity. Native bidder, notice-review, workshare and capture conflicts are inspected before completion; command conflicts remain visible even when historical record reads succeed. The original saved workshare is read back and compared in full, including scope, acceptance, source context and all history. The final result identifies the package, receiving workspace and decision.

A source or reviewer change is preserved. Resolve the displayed current context using the existing desk; do not discard the original database or fabricate replacement records. A definitive revision conflict means the prepared unchanged command needs review before updating its expected revision. The operating code does not silently rewrite an existing decision.
