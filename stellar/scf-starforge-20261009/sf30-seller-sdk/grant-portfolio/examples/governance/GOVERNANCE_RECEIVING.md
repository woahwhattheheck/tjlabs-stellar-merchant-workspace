# Complete original-case governance receiving

Run this programme only with the actual original case archive and reviewed governance actions. It borrows three already running, separately owned Grant Portfolio consoles: producer, recipient and return. Their existing owners retain the server/database/process lifetimes. The programme owns its three authenticated client lifetimes, exact input, output receipts and downloads.

No committee members, evaluation finding, decision, authority, date or financial input is manufactured by the programme.

## Prepare the complete selected input

The JSON schema is stellar-forge.governance-receiving.v1.

- operationId is one stable receiving identity, at most 111 simple identifier characters. Keep it unchanged on continuation.
- authorization is the actual internal programme/case reference.
- connections has producer, recipient and return: absolute paths to the original private console connection JSON files.
- archive has the absolute original complete portfolio ZIP path, byte length and SHA-256.
- portfolio has the original saved id, revision and snapshot.
- steps is the complete ordered list of original portfolio.save action objects. Each uses its stable operationId, actual portfolio predecessor revision and governance changes.
- recipientAction is the actual reviewed following portfolio.save action on the completed producer revision.

The original request object is unchanged: operationId, action, payload and optional original workspace expectedRevision. Its payload selects the actual portfolio ID/revision and governance revision. Preserve the original name, notes, sources and review fields required by portfolio.save. Governance can compose programme changes for actual evidence documents in the same save. Documents referenced by these actions must already be retained or supplied through the maintained source import workflow.

Every request ID is unique across producer, recipient and the receiving programme's generated original import/export IDs. The input is retained byte-for-byte before any operation. The programme refuses replacement input in the same output directory.

The original producer steps must result in actual recorded editions in all seven registers. A smaller real case is valid product data, but cannot be reported as this complete seven-register receiving journey. Select the existing authorised case and supply the remaining actual reviewed material; do not fill missing customer records with invented data.

## Invoke once, then continue the same operation

```sh
node grant-portfolio/examples/governance/governance-receiving.mjs \
  --input /absolute/private/original-governance-input.json \
  --out /absolute/private/original-governance-receiving
```

Use a private operation directory. Repeat that exact command after an interruption, keeping the original input and console workspace identities. The original server returns the saved result for the same request before checking later revisions. No automatic new operation ID or replacement workspace is created.

The programme does not launch or stop the borrowed servers. Coordinate with their existing owner so one business programme owns the selected actual case and any other activity is explicit. Do not run a competing receiving caller in the same output directory.

## Whole journey and evidence

1. Bind the three distinct original workspace IDs and original archive bytes.
2. Receive the original archive and read the exact source portfolio.
3. Apply each full reviewed governance action under its original identity, immediately checking same-request replay.
4. Read all seven complete registers, every record/history/dependency review and selected evidence document bytes.
5. Export the complete producer archive.
6. Receive it into the independent recipient and reopen the exact whole portfolio.
7. Apply the actual recipient edit and reopen all resulting records/history.
8. Replay the original earlier receive, verifying both its selected historical portfolio and the full latest recipient revision remain unchanged.
9. Export the complete edited return archive, receive it into the third workspace, and reopen the whole final history.

Each stage retains complete request/result bodies. Every observed response uses its content hash; only a completed response receives the immutable accepted-response selection. A retryable failed response therefore stays retained without blocking the same request's later completion. A completed stage records its whole artifact index and input identity. Continuation rehashes those files and adopts the original observation instead of recomputing it against later customer work. A completed whole report must retain all required ordered stages and every original artifact before adoption; it does not rerun business requests. Document/ZIP downloads use the original streaming client and full length/SHA validation. Local artifact publication is create-only with file and parent synchronization. Existing exact output is reused; conflicting output stops continuation.

COMPLETE.json is written only after the complete journey and client closure. An interrupted attempt retains an INTERRUPTED-SHA.json report and its exact completed artifacts. A service error or lost response is not a new business identity. Read the original server request and preserve the interrupted report before continuing.

The output input and connection-file locators are private operational data; do not place actual customer inputs or connection files in the generic source repository. Publish the complete actual receiving package only to the existing authorised private destination and original case owner. The code and this parameter contract are reusable source.

## What this verifies

The programme checks the actual original save/request/portable APIs, all recorded publications, complete document custody, historical reader consistency, preserved recipient edits and independent return. It does not claim an SPC deployment, customer policy approval, native staff clearance, bank action, automatic milestone closure or meeting/evaluation occurrence.

Browser import/edit usability is covered by the full mounted source review and the existing console flow. The programme intentionally consumes supplied complete actions; it does not substitute a second synthetic evaluation model for actual customer input.
