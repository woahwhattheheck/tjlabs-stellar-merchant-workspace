# dbt project results through the original dataset publisher

The dbt project retains the source manifest, node selection, result bytes, SQL and
complete publisher provenance in one editable handover. Query execution, source
connection, immutable extraction plans, review and dataset publication belong to
the existing PostgreSQL or SQLite publisher. The dbt bridge adds context and
receiving, rather than running a second query engine.

## Run the whole native customer journey

On Linux with Node 22 or later, Python 3 and util-linux `flock`:

```sh
node sf30-seller-sdk/dbt-artifacts/EXERCISE_PUBLISHER.mjs --work /absolute/new-journey
```

Run from `stellar/scf-starforge-20261009`. The destination must be new. The command
creates an example SQLite warehouse with 1,000 rows, identifiers above 2^53,
exact decimal text, quoted Unicode text and nulls. It creates the dbt project,
imports its authored matching manifest, saves an original publisher plan and
extracts the entire result in an original read transaction. The normal query's
two-row preview ceiling does not truncate that complete retained extraction.

It then reviews and publishes through the original dataset version writer,
binds the exact CSV/query/provenance to the selected dbt node, repeats the same
run ID without rerunning the query, closes/reopens, exports JSON/CSV/HTML and a
complete editable ZIP, removes only its own new sender tree, receives the ZIP
and creates review revision two. `result.json` records the concrete original run,
plan, edition, published snapshot and complete file identities. The published
dataset remains in `published-dataset`; the editable recipient is `received`.

The 12 October 2026 native run retained all 1,000 rows and 54,272 CSV bytes. The
result SHA-256 is `97493b14d1d1262b902946e62edf6c33e161b6edfd7ccf9385220f4b5e4fb371`.
The example's source is an authored local warehouse; a customer's chosen
warehouse and dbt artifacts enter through the same original interfaces below.

## Install and open the native product

Install the complete source-built merchant package supplied with the delivery:

```sh
mkdir merchant-customer
cd merchant-customer
npm install --ignore-scripts --offline --omit=optional --no-audit --no-fund /absolute/merchant-package.tgz
./node_modules/.bin/starforge dbt-project --help
```

The SQLite journey uses built-in Node and Python modules. PostgreSQL uses the
existing publisher's selected `pg`/`pg-cursor` dependencies and private
connection environment; install those through the maintained runtime profile
for your product rather than including a password in a source packet.

## Select a project and an original publisher

Initialize/import the original project with the existing command:

```sh
starforge dbt-project --project /absolute/project create --title 'Customer dbt review'
starforge dbt-project --project /absolute/project import /absolute/manifest.json
```

Save an edition through `invoke edition.create --input edition.json`, selecting
the imported manifest ID and optional catalog/run/freshness IDs. Importing the
original files does not select or execute arbitrary SQL automatically.

A private native publisher configuration selects these paths:

```json
{
  "project": "/absolute/project",
  "publisherDirectory": "/absolute/publisher",
  "sourceFile": "/absolute/original-source.json",
  "targetDirectory": "/absolute/dataset-target",
  "create": true
}
```

Use `create: true` once. Reopening uses the original project and
publisherDirectory with `create: false`; its original source and target are
read from the retained publisher workspace. Choose `sqlite` or `postgres`:

```sh
starforge dbt-project sqlite source --config publisher.json
starforge dbt-project sqlite plan.save --config reopened-publisher.json --input plan.json
starforge dbt-project sqlite extract --config reopened-publisher.json --input extract.json
starforge dbt-project sqlite inspect --config reopened-publisher.json --input run.json
```

The original plan includes `sourceHash`, named `query`, selected parameter
`input`, typed `dataset` columns and full-extraction `order` and limits. The
complete example in `EXERCISE_PUBLISHER.mjs` demonstrates every supplied field.
Use strings for exact integers beyond JavaScript's safe integer range and for
exact decimal text; nullability is an explicit dataset-column selection.

Save `extract.json` with `plan` and a newly chosen UUID `id`. Repeating the same
plan/UUID reads its original run; it does not issue another warehouse query.
A different plan with that ID is rejected. Inspect the original run before using
`recover`, and select a new UUID deliberately for a genuinely new extraction.

## Review, publish and bind the retained result

`review` receives `{id, review: {reviewer, note, initialize: true}}` for a new
dataset target. Updating an existing running target instead passes the
original expected snapshot and revision. `publish` receives `{id, reviewId}`
from that exact recorded review. Read the returned native state: a successful
publication is `PUBLISHED`.

`bind` receives this exact selected context:

```json
{
  "id": "ORIGINAL-PUBLISHER-RUN-UUID",
  "edition": "DBT-EDITION-SHA256",
  "uid": "model.customer.selected_model",
  "request_id": "customer-result-binding-001",
  "expectedQueryHash": "ORIGINAL-PLAN-QUERY-SHA256",
  "expectedCandidateHash": "ORIGINAL-CANDIDATE-DIGEST"
}
```

The binding reads the original candidate through its publisher validator,
retains all CSV bytes and SQL, and records the source/plan/query/candidate
identities plus the original read-transaction result. Repeating the request ID
with the same selection recovers its stored result. The link is an explicit
operator-selected dbt context; a matching file name is not an automatic link.

The JavaScript/TypeScript exports are:

```js
import { DbtSqliteProject } from '@tokenjunkielabs/starforge-merchant/seller/dbt-project/publisher';
import { DbtPostgresProject } from '@tokenjunkielabs/starforge-merchant/seller/dbt-project/postgres';
import { DbtProjectClient } from '@tokenjunkielabs/starforge-merchant/seller/dbt-project';
```

Choose the package name emitted by your maintained build when its product
selection overrides the default. Both native bridge classes expose
`open(options)`, `call(action,input)` and `close()`. Closing drains already
accepted callbacks before releasing the original publisher lease. Explicit
`cancel` remains the original extraction cancellation operation.

## Receive and continue independently

Use the existing project's export action to create a complete ZIP. Retain the
returned archive SHA-256 with it. The recipient does not need the sender's
project, native publisher directory or warehouse connection:

```sh
starforge dbt-project receive /absolute/project.zip --destination /absolute/new-project --expected-sha ARCHIVE_SHA256
starforge dbt-project --project /absolute/new-project status
starforge dbt-project --project /absolute/new-project serve --port 0
```

`DbtProjectClient.receive()` uses that same source-independent Python receive
command, so the destination can be absent and the sender can already be removed.
The receiver creates a complete original project, preserves its identity,
reports, source artifacts, review history and bound result objects, and can save
the next checked review revision. `copyObject()` creates complete verified files
without overwriting an existing destination. The original dataset's versioned
server remains a separate deployment with its original lifecycle.
