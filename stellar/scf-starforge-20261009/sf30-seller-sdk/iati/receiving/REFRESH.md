# Complete publisher-refresh receiving

This procedure operates the installed IATI workspace from complete retained publisher XML. It exercises the saved plan, original native portfolio operation, explicit review, baseline promotion, full archive, independent receiving and later-work preservation. It does not fetch another publisher, invent a replacement edition, or start a second native scheduler.

The full customer product is described in [../REFRESH.md](../REFRESH.md). The original installation procedure is [RUNTIME.md](RUNTIME.md); the selected runtime recipe includes the entire IATI source directory, its original XML/native engine and the full Applications interface.

## What the complete workflow proves

The original Python procedure first ingests both full caller-selected XML files and retains their byte counts, SHA-256 identities, labels and supplied provenance. The caller decides whether the two files represent different publisher editions. Selecting identical bytes is valid: the resulting comparison must honestly remain an unchanged-source observation.

It creates a reviewed native baseline and saves a refresh plan. It then exercises the actual lost-reply boundary by allowing the original native portfolio save to commit, recording the complete returned pointer, and interrupting only its return to the refresh caller. A later ordinary native portfolio edit advances the current head. Resuming the exact retained refresh request must still return its original earlier candidate, not that mutable head. The workflow cancels this explicitly selected receiving run without erasing its native history.

The next run executes a complete preview and original candidate/comparison, records the supplied named review, and explicitly promotes that reviewed pointer. Pausing and reactivating the plan must retain the same baseline. A final new request is prepared and interrupted before its native save. This request remains pending in the original workspace and is included in its complete exported packet.

The procedure closes that workspace before receiving the packet into the selected independent workspace. It repeats the same receive, resumes the same pending request there, then cancels that receiving run. Importing the older original packet again must preserve the later local history. Both workspaces are reopened sequentially and the full JSON, HTML and CSV reports are extracted and verified against their native packet manifests.

The Node procedure adds the real installed operator surfaces. It opens the original Applications entries on the same closed source and received workspaces, reads complete snapshot-pinned histories through the typed client and authenticated MCP transport, returns complete native ZIP files through the bounded retained reader, and runs the original CLI after each application is stopped. The desktop and mobile browser uses the actual saved-plan, preview, run, named review, promotion and complete receiving interface. A separate browser-created plan preserves the original core plan and its pending source request. Finally the original Applications entries are stopped and reopened, and the complete customer carrier retains the exact source, action, export and receiving records. Browser screenshots remain private QA files.

These are different completion facts. A published source package or a successful syntax check does not establish that the complete native workflow ran. Accept a receiving result only when its state is COMPLETE, its selected runtime/input identities match, every listed output exists with the recorded full byte count and SHA-256, and the original native controller has returned its actual terminal result.

The numbers, digests, dates, URLs and names above are placeholders. Replace them with the actual selected originals. The receiving operation preserves these inputs and rejects changed file bytes on retry. Do not relabel historical research data as current publisher data. The bundled historical AidData release and the separately retained Transparency International publisher file keep their original source notices; choosing one unchanged file twice proves repeat receiving, not freshness.

Optional fields are name, selection, nextSelection, sourceChangeNote and selectionNote. selection is the original IATI portfolio selection used by the baseline. nextSelection is the explicit candidate selection. Supported keys are activityIds, currencies, transactionTypes, budgetTypes, dateFrom and dateTo, with the same original native rules. A changed selection requires a substantive selectionNote. The report keeps scope changes separate from keyed record differences. An unpaired source addition/removal needs sourceChangeNote; ordinary one-to-one replacement is represented explicitly in the preview.

Create the private parent directories first. The workflow creates its own fresh workspaces when they are absent. It opens an existing selected workspace only as continuation of the exact retained operation and source selection. Keep every original workspace, action file, partial output and native record until the same receiving result is complete.

Run the complete core directly when only the original-model receiving is required:

    python3 -B /absolute/ready-runtime/package/source/stellar/scf-starforge-20261009/sf30-seller-sdk/iati/receiving/refresh.py --input /absolute/core-input.json

For the full installed/browser workflow, let the Node procedure invoke and reconcile this exact same core input. Do not run a second core operation in parallel.

## Continuation after interruption

Reuse the same complete inputs, installed source, operation IDs and selected output directories. The original native controller remains the launch authority. This procedure does not create another native job, rewrite an old admission record or infer that a lost terminal means the original process has ended.

The core's selection.json pins its complete input and critical original source files. Every action retains a full input before dispatch and its exact result after the original API returns. The two deliberate boundary observations are part of this declared receiving scenario; they do not simulate publisher data or manufacture an engine result. The pending source request is retained as PREPARED and can later be resumed or explicitly abandoned through the product.

A completed core-summary.json is verified before any model is reopened. Its full selected files are reused while an interrupted customer ZIP is completed. The original packet writer verifies the existing final ZIP or retains the original partial attempt before continuation. No completed source or request is discarded to make the receiving appear fresh.

The operator similarly selects a completed bundle intent before repeating any completed UI or Applications leg. Action request/result companions are reconciled before a new browser UUID can be chosen. Retained download prefixes are verified against the selected original SHA and resumed through a new original read handle after interruption. New QA attempts use distinct filenames; they do not overwrite evidence selected by a completed summary.

If a native action is still uncertain, keep its original request and runtime records. Read refresh-request or refresh-status before deciding what to resume. A PREPARED record with a committed native result must use resume; it cannot be abandoned. An older compatible receive preserves later plan/run/action history and reports both packet and current plan/snapshot identities.

Its files have absolute paths, full bytes and SHA-256 values. The actual outer native result must be retained alongside it.

The full operator ZIP contains the original core customer packet, both complete source/received refresh packets, full publisher inputs/provenance, final CLI and remote archives, saved browser action bodies/results, complete runtime/source binding observations and the usable product/receiving guides. It includes original report files, not just a rendered screenshot or excerpt. Private browser PNGs remain separate QA outputs.

## Reading the financial result

The preview and comparison counts are source/activity/transaction/budget row counts. They are not financial totals. Exact amount strings remain grouped by the original reporter, hierarchy, currency, transaction type, value date and budget period. Do not add incompatible groups or describe an unchanged selected file as a new reporting period.

A source replacement, an added/removed publisher and a changed activity/finance filter are different decisions. The original plan and run record all three explicitly. Native report and archive comparisons retain their full identities even when the current portfolio has later edits. Promotion changes the saved baseline only after the explicit named decision.

Use the complete report and history when handing work to a colleague. The initial packet can be independently received and its pending request continued with the original selection. The later received packet can in turn be exported and reopened without losing the original baseline or the intervening review decisions.
