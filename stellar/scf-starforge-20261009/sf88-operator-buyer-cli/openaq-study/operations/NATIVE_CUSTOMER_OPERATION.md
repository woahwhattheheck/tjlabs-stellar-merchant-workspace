# OpenAQ native customer operation

This operating case joins the released OpenAQ merchant and customer console to the original Stellar testnet payment path. It purchases the already retained Del Norte dataset in three pages, obtains one original approval for each page, reconciles the resulting transfers, exports the complete dataset and study, and reopens that delivery in a separate receiving console.

## Transport and owned lifetime

The host uses the installed Node runtime and retained Chromium binary. Its temporary browser profile, native state and output reserve are private to this operation. The approval broker uses a short private Unix-socket root to remain within the original broker's path limit.

The local TLS endpoint forwards to the actual original merchant listener. The buyer's explicit CONNECT proxy permits that exact merchant authority and the original soroban-testnet.stellar.org:443 finality endpoint. RPC TLS remains end to end and uses the environment's existing proxy when required. The original finalizer uses its documented system-CA option. The driver supplies no replacement payment verifier, settlement implementation or RPC result.

The application owns and drains its customer and receiving clients, both consoles, browser context and browser, local transport, merchant workspace and facilitator. It records cleanup failures with the original outcome. The host reserves space for its terminal result before application dispatch and saves the complete delivery and private recovery separately before exit. It updates the same three saved artifact identities with their observed version numbers. Each continuation retains the preceding outcome and source identity in its history. Browser screenshots remain local to the owned process for inspection and are excluded from delivered archives.

## Receiving the result

The terminal record is outputs/result.json, with the enclosing native outcome in outputs/native-host.json. Successful completion requires state COMPLETE in both and actual accounting entries; authored source and source import success do not establish a payment.

OpenAQ_Native_Customer_Delivery_20261012.zip carries the customer delivery, operating output and source manifest. OpenAQ_Native_Customer_Private_Recovery_20261012.zip retains the original operator wallets, approval journals, source project and private configuration for recovery. The recovery archive belongs to Bryce's private custody and is separate from customer-facing delivery.

If execution is interrupted, inspect the original native process and retained request, buyer and accounting states before continuing. A lost interactive session does not itself identify the application's terminal state. The saved recovery edition includes the original wallets, request and study; restore that edition rather than initializing replacement custody. The host checks the original operation, directory, wallet addresses and predecessor source before a pre-payment continuation. A completed operation reopens its saved result. An uncertain payment is handled by the original SF36 recovery path using its existing intent and authorization; creating a second payer or replacing an unresolved request would lose that original relationship.

## Operating files

- `operate-native-customer.mjs` owns this original merchant/customer sequence and delegates payment, approval, finality, dataset handling and receiving to the released modules.
- `native-customer-host.py` accepts the base64-encoded gzip JSON control as its one argument. The control names the prepared runtime, original project, retained Chrome, source manifest, driver bytes/hash, exact input archive, time limit and private output reserve. A continuation additionally carries the pinned saved archive editions, original public wallet identities, predecessor source hash and the three existing output IDs/versions.
- The control and any signed transfer URLs are private runtime inputs. Wallet material is only in the private recovery archive. The source files contain no wallet secrets.

Use the original installed runtime and current transfer preparation to assemble the control. The host's `resume` branch is for a saved pre-payment failure with all owned resources closed. Once a Buyer authorization or payment exists, use the original Buyer/SF36 recovery state before choosing any continuation; this host does not discard that state or create a new payment operation.
