## What the operator completes

1. Open the original completed case with the current application and its original private case directory.
2. Review the existing retired incident and its retained capture in the HTTP interface.
3. Save a consistent snapshot of the complete original incident store. The maintained implementation pins the exact source revision and capture references during copying.
4. Inspect the complete snapshot through the recovery desk, including every selected file.
5. Receive the snapshot into a separate private directory and open that received store in the same Support interface.
6. Review the received original incident and construct its native Support handoff from the actual retained capture.
7. Reconcile the received store against the exact displayed recovery ID, manifest, configuration and notification queue.
8. Add the completed recovery work to the original case while preserving its original workspace, both complete Object captures and existing case history.
9. Export the complete case, close the operating process, and start a separate original Support process with its own case store and an empty incident profile.
10. Import, save and reopen the same case ID there, review both Object captures, export the complete receiving handoff and close the process.
11. Package all current source, the complete recovery stores, the original Object session, the original full baseline package, the case handoffs and the operating source.
12. Save that complete package through the existing Library workflow and retain the actual returned file identity.

The original incident concerns the 266-byte workload configuration applied to the acquired 267-byte Object. The original customer retired that incident with CONFIGURATION_CHANGED and took a fresh complete observation under the reviewed workload. This programme preserves that explanation in the continued case.

The selected original configuration has no notification destination and no notification entries. The programme confirms that state from the actual snapshot. Queue reconciliation records the receiving operator's action; this customer journey sends no notification.

## Continue an interrupted operation

Use the same private programme configuration and original operation.

The source receiver reuses the exact received objects and source root. The recovery desk's snapshot, receive and reconciliation calls retain their original operation IDs and saved request bodies. Repeating those exact application operations invokes their maintained continuation behaviour.

Opening a received profile is repeated for each fresh Support process because an open profile belongs to that process. The programme does not substitute a cached open result for registering the actual received store.

Case writes retain the full request before dispatch. On continuation, the programme reads the same case ID first. If the actual saved workspace, support data and metadata match the prepared request, it adopts that saved revision. Otherwise, the original expected revision must still match before the existing case API may save it. A conflicting case is preserved for integration with its current owner.

The native customer closes its own Support children during cleanup. The outer programme also owns the complete child process group, retains the unreaped leader through termination, and closes the group before releasing the programme lock after a timeout or cancellation. The completed customer's result is reused for packaging; a completed programme is reported from its retained delivery result.

The package save records its complete prepare/finalize calls separately under library-calls. If a save result is already present, it is checked and reused. If the transport ended after a save dispatch and before its result, use the retained calls and the actual saved file metadata to reconcile that dispatch. The complete native package remains available for that work.
