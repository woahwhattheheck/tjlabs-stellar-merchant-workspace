# Implementation and receiving plan

## Days 1–2: selected authority and original baseline

Receive the selected Medusa/plugin/runtime version, Dynamics Sales environment, existing integration source and deployment record, schema/field mapping, original idempotency/upsert behavior, ambiguity queue, one bounded export scope and reviewer. Name the prime/customer/data owners and actual access boundaries. Bind the original source commit, immutable export hashes and selection/page completeness evidence. Confirm whether money is expressed as major or minor units; configure the actual currency scales explicitly.

The baseline defines one order-flow success, missing-counterpart and conflict/recovery course. Use authorized staging or appropriately sanitized source, retaining the transformation reference. A completed integration is not presumed broken. Identify the exact needed change or confirm that its native behavior is already adequate.

## Days 3–5: capture adapter and receiving

Implement the selected source adapter around the existing official API/export interfaces, with original source version and completeness metadata. Keep the twelve-field maximum and one selected flow. Map one explicit key per side; duplicate keys become review findings. Do not silently choose one row or change customer identity from email matching. Preserve exact decimal strings and currency-specific minor-unit totals. Keep customer/status comparison opt-in and explicit.

Use the supplied browser and CLI to produce the complete original package. Retain reviewer decisions against its canonical input hash. A changed source requires a new analysis and review; the original remains available. Attach the result to the existing saved case with its retained request ID, actor, first timestamp and expected case revision. Demonstrate original event replay after a lost receipt without another material.

## Days 6–8: selected recovery change and rollout

Implement at most one selected recovery change in the existing integration source. For an ambiguous customer, route through the current review mechanism. For a returned or uncertain order write, inspect the original downstream key/result before deciding whether the same original operation can continue. Never create another customer or order merely because a local response was lost. Customer source and native API semantics determine the concrete implementation.

Receive the source change through Rigby's normal review and staging release. Record before-state, original operation IDs, actual response, source/destination readback and the effect on the selected field mapping. Exercise the existing recovery route with one permitted bounded observation. Prepare exact rollback steps that preserve unrelated later records and require reconciliation if another operator changed the same record.

## Days 9–10: production selection and independent receiving

Use the actual production change window and named release owner. Reopen the selected source and original request before any retry. Receive the selected real output and record open findings honestly. Export the full original saved case, all historical editions, every attached original source and the complete integration/reconciliation source. Reopen into a separate receiving directory through the existing package receiver and verify original files, history and review identities. Run the 75-minute operator handover.

Customer acceptance is the named receiver's explicit decision against Acceptance.csv. The product's REVIEW_RECORDED state only means an operator's dispositions have been saved. It is not a success assertion about remote systems or an accepted invoice.
