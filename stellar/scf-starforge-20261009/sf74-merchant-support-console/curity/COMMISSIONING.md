# Curity: complete original-service commissioning

This programme operates the original OAuth observer, the original SF93 incident source and the native SF74 case console. It receives both exact published Curity log examples, freezes their reviewed mappings, compares the whole source, carries both editions with the case, and operates independent receiving, reopening and selective rollback.

Run `curity/commissioning.mjs` from the complete selected application. Node 22+, Python used by the original native source receiver, and Linux `flock` are required. Importing the module does not start a service. The CLI holds one process lock for the complete original operation. Repeating the same plan resumes its retained identities and phases.

## Select the original host

Use the existing host's protected loopback observation endpoint and its already configured bearer-token environment-variable **name**. Read the existing SF93 source profile to select the original source ID, incident ID and merchant-registration route. The source profile may contain trusted `oauthResources` startup registrations; browser requests select registered source IDs. Retain the existing watch, incident store, verifier and host-authority callback.

The programme reads the original protected observer through `reviewOAuthSource` and `readOAuthSource`. It does not initialize another incident watcher or dispatch replacement service processes. It prepares the selected actual incident with the original incident desk and imports that desk's complete native runtime handoff. The new case lives in the selected internal commissioning case store; later staff-edit scenarios are performed by the programme on that dedicated case.

Select the exact serialized SF74 workspace whose native inputs and route apply to the incident. Keep its six original source slots. The OAuth runtime integration accepts and retains both original OAuth capture files through the unchanged runtime-support schema.

An existing original incident and workspace are programme inputs, just as an existing OAuth resource is. Select these from the maintained host; there are no embedded customer identifiers or credentials in this source package.

## Run and resume

```sh
node stellar/scf-starforge-20261009/sf74-merchant-support-console/curity/commissioning.mjs /absolute/selected-plan.json
```

The command prints the completed report location, original and recipient native case IDs, and returned complete package location. Both local consoles close on completion. Their durable case and companion directories remain ready to reopen with the same operator launcher.

After interruption, run the **same command with the same plan**. The original operation identities in `IDENTITY.json`, original native case UUID, source input IDs, bridge operation IDs, export IDs, receiving request ID and rollback ID remain fixed. Each phase retains its complete input before dispatch and its result afterward. Existing source editions and native receiver operations are reconciled by the original implementation.

Read status without starting either console:

```sh
node stellar/scf-starforge-20261009/sf74-merchant-support-console/curity/commissioning.mjs status /absolute/original-operation
```

A second overlapping CLI invocation cannot take the held native lock. An absent complete report is not interpreted as a successful run.

## What the programme completes

1. Verifies the complete selected readable application and retains the exact plan and all operation identities.
2. Reviews and reads the actual original protected OAuth observation, retaining its original bytes and reviewed resource/configuration.
3. Prepares the actual selected SF93 incident through the native incident desk, imports its full runtime handoff, and creates one dedicated native commissioning case with a retained UUID and exact null creation revision.
4. Receives the original published JSONLayout example, confirms the complete one-event interpretation, and retains the event ID and `.615014186` instant without rounding.
5. Freezes a reviewed immutable edition and attaches its original occurrence to the native case through the revision-guarded bridge.
6. Writes an explicit programme-authored staff-edit scenario in that case, then receives the following structured example. Its published outer empty message remains distinct from missing or null data.
7. Freezes the following mapping and review, compares **all** classifiable identities/content/occurrences, and separately compares the reviewed selection. Different typed content under the same event ID is reported; it is not silently declared identical.
8. Attaches the following source edition while retaining the intervening note, then writes later staff-owned next-action and notes values. The original comparison must identify the changed owned field.
9. Exports the whole current native case and its complete companion closure. Both earlier and following source editions, retained bridge history and the actual application are carried together.
10. Receives into an independent native store, verifies that both source editions reopen completely, and records the actual returned case identity.
11. Adds recipient staff work, closes and reopens the original recipient operator, and replays the original receiving request. Its original receipt remains stable and later staff values remain unchanged.
12. Selectively rolls back the accepted source changes using the recipient's fresh native revision. Later staff-owned next action and notes survive; at least one untouched source-owned field is restored. Original workspace/support bytes remain unchanged.
13. Exports the complete returned case and saves the full commissioning result.

This is a continuous application workflow. The source assertions at the joins protect useful behavior—exact mapping, complete source transfer, stable receiving and preservation of staff work. They are part of the operation rather than a separate generated test suite.

## Output

`COMMISSIONING.json` is written only after the complete journey succeeds. It contains the retained plan identity; application inventory; actual observer source; original incident selection; initial and following editions; whole-source and selected-source comparisons; native attachment results; performed staff-edit scenarios; sender export; original receiving and replay; reopening comparisons; rollback restored/skipped fields; and the complete returned package.

The directory also retains:

- `PLAN.json` and `IDENTITY.json`;
- the complete original publisher packet and both exact interpreted source representations;
- original observer bytes and source review;
- original incident runtime handoff, readable report and native report data;
- original inputs/results for every durable operation phase;
- `complete-source-comparison/changes.jsonl` and its digest-bound comparison manifest;
- the independent reviewed-selection comparison.

Initial and following original exports share a combined one-GiB budget. The two publisher files are counted once. Mapping/review editions reuse those exact originals, and source manifests report their complete framing/accounting. Native case histories and all original source bytes remain available after rollback.

The input context remains `PUBLISHER_EXAMPLE`. The result records programme-authored staff-edit scenarios and an operated existing host workflow; customer installation acceptance and commercial acceptance are not asserted by those examples. The original commercial operation and supplier relationship remain `DBC61-CURITY-OAUTH-SUPPORT-WORKSHARE-20261013`.
