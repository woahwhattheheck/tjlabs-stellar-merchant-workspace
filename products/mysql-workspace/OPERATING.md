# MySQL operating and receiving guide

## One selected product

An initialized product is the durable customer unit. Its UUID and source hash are stable across process restart and portable receiving. The original merchant host acquires one product lease, creates one schema-driven editor, and owns the native publication and seller instances opened through that product.

Use the complete browser URL returned by the current foreground owner. Its capability fragment belongs to that listener. Agents read the current private `connection.json` before every action and bind the original product UUID and workspace alias. A restart changes native instance and endpoint identifiers; the product identity and retained work stay the same.

Private credentials are environment references. Restore the configured database password reference and merchant token reference in the receiving environment. The copied CA and exact configured host/database/user remain part of source review.

Generated copies in `receiving/`, ephemeral capabilities, native process lock files and redundant merchant customer-export copies are omitted from the next archive. Source state, empty native directories, file modes and exact original customer-client bytes remain included.

The original publisher stores paths relative to its own ledger only when this trusted product initializes it. Existing standalone publisher settings keep their original absolute-path behavior. Receiving never edits an original plan, candidate, request, source hash, payment choice or buyer intent to make it fit another location.

## Staff authoring procedure

1. Initialize from the reviewed MySQL declaration and existing environment references.
2. Open the actual database catalog. Select a table, exact public columns, supported typed filters and explicit ordering.
3. Add endpoints to the release, enter the public HTTPS origin and complete native payment choices, and save the current working editor with a meaningful version note.
4. Run the original source review and private example. Review the SQL, scalar casts, route contract and native terms, then prepare the immutable release.
5. Reopen the original manifest, run the source-native SQL seller when intended, and export the prepared Node customer client/OpenAPI package.
6. Save another working version before changing the next release. The previous selected draft/version remains reopenable.

Draft storage accepts unfinished editor values. Preparation always returns to the original MySQL compiler and fresh schema contract. Stale columns are explained during editor reopen while their original saved version stays unchanged. Saving a historical draft checks its historical revision; use a separate draft or reopen the latest head after a conflict.

The browser persists original product mutation input before dispatch. **Read saved outcome** checks the native original action, and **Resume original action** sends exactly that request and input again. A request UUID cannot be reassigned to different input. Paginated saved-action and draft-version views retain older work.

## Publisher and payment sequence

A publication is selected by prepared release ID, plan ID, manifest hash and exact source hash. Create it from the selected release. Its native publisher uses that release’s approved MySQL source and a fixed dataset target under the same product.

In the original publisher:

1. Inspect the source hash and approved named queries.
2. Save the exact public column types, filtering/range/sort contract, parameter input, source limits and deterministic extraction order.
3. Start extraction with its original run UUID.
4. Inspect the completed candidate and original transaction/row/byte results.
5. Record the candidate reviewer and note. First publication selects an absent dataset target; later publication selects the current snapshot and revision.
6. Publish using the returned exact native review UUID.

The product’s **Versioned dataset seller** panel reads the current original target. Its configuration review chooses one payment alternative from the prepared release, a dataset route, current snapshot and revision, reviewer and note. The same original seller compiler validates those native terms, including their extra fields. The route adds the original optional snapshot selector.

Start selects both the retained configuration SHA-256 and currently observed target snapshot/revision. The original dataset version owner and loopback control connection remain the sole writer. The publisher uses that control connection for live publication and reads the actual resulting target state.

The seller’s actual reported mode and current endpoints remain visible. Configure a native facilitator when the operating payment flow requires one. Query filters, admission, payment, settlement and CSV paging stay with the original engines.

For consistent source snapshots, review the underlying storage engine. The source transaction requests repeatable-read, read-only and consistent snapshot. InnoDB provides transactional snapshot behavior; a query involving nontransactional tables needs its own explicit source assessment. The retained extraction report records the actual original transaction information.

## Buyer acquisition and recurring publication

**Buyer handoff** reads the actual running seller health and offer for a retained candidate snapshot. The original offer reader verifies the advertised GET resource, native admission hook and optional snapshot query field. Staff selects the displayed native payment alternative and a unique customer intent ID.

Preparing a buyer handoff retains the exact SF88 config bytes and original publisher event. It preserves the snapshot, offer digest, intent and config hash. Reopen older handoffs from the original paged event history. The receiving product resolves their retained relative file identity and verifies the original event digest before returning those bytes.

Use the original Buyer workspace or CLI to continue the selected customer acquisition. That workflow owns signing, actual authorization/payment and retained customer delivery. Keep its successful transaction and original intent when investigating an interrupted response.

Recurring publication is configured through the original publisher browser or the `merchant_mysql_product_publish_schedule_*` tools. Review its exact baseline run, plan digest, target snapshot/revision, row limits, error policy and operator note. An enabled policy resumes when its original publication is opened. Pause preserves an accepted occurrence; native cancellation and pending-occurrence recovery remain explicit original actions.

## Recovery controls

| Situation | Continue from |
| --- | --- |
| Browser lost a saved draft or configuration response | Original product request UUID and saved input |
| Source review expired | Current original editor review of the retained working choices |
| Native extraction was interrupted | Original run/candidate and native inspect/recover controls |
| Publication response was lost | Original run/review and observed target snapshot/revision |
| Buyer configuration response was lost | Original run’s buyer-handoff event and verified saved configuration |
| Product process restarted | Current private connection plus the same product UUID |
| Complete archive reply was lost | Original transfer request; a complete already-written archive is inspected and adopted |
| Download interrupted | Original retained-file checkpoint, manifest digest, file digest and exact byte offset |
| Receive repeated after later customer work | Original receiving receipt; subsequent destination work is preserved |

Original publisher writes that do not provide their own replay identity are shown as retained browser attempts with native inspection controls. Read the native saved plans, runs or handoff events before creating another action. Product saving and archive/configuration mutations expose exact UUID-based recovery.

## Complete handover and reopen

1. Choose **Create complete handover**. The product serializes against current product actions and closes each original native owner. Publication recurrence, extraction and active sellers finish or cancel through their existing close behavior.
2. The original product lease stays held while the complete native state is inventoried and streamed. All files, directory modes, source identities and digests enter one manifest.
3. The archive is fsynced and retained under the original transfer UUID. The product then reopens its editor and exposes the existing action result.
4. Download that exact archive with the browser’s single-use ticket or original retained-file client. The browser verifies the retained descriptor before streaming; the agent transfer keeps chunk, prefix and whole-file checks.
5. Inspect and select the exact compressed archive hash and original product UUID. Restore to a new private directory.
6. The same archive parser verifies each declared member, type, path, size, mode, digest and complete gzip/tar ending before publishing the destination. Empty directories are restored.
7. Supply the receiving environment references and open the received product. Read its saved drafts, releases, customer clients, candidate and buyer history. Reopen selected publications and start reviewed sellers explicitly.

The parser accepts regular files and declared directories only. It rejects links, devices, traversal, duplicate/conflicting paths, undeclared entries, truncation and trailing content. The staged destination is published after full validation. A received archive preserves the original operational data and records the new receiving event separately.

One compressed native MCP file may be up to 8 GiB. The streamed archive supports up to 32 GiB of file content within the documented per-member and entry-count limits. Use the existing private file transfer or browser download when the compressed archive exceeds the native MCP reader limit.

## Installed Applications and source support

Select **MySQL merchant workspace** in the original Applications console. Its operating review includes product/source/configuration files, source credential reference, original directory identities and selected transport settings. The retained startup binding and returned listener endpoints must match that reviewed request. Common process preparation appends the selected port exactly once.

The source-selection contribution retains the complete native MySQL driver/package, original publisher browser and scheduler, dataset version writer, Buyer workflow, merchant/MCP transport, Applications and customer-client delivery support. The product ships its own browser assets, Node client, CLI, provider/catalog, receiver and guides alongside those original components.

The complete source-native receiving result is recorded separately from this operating guide. Keep the selected source revision, original native operation and output identity together when handing the product to another operator.
