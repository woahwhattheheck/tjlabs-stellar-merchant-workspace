# Institutional repository services and Stellar delivery

The maintained `tind-migration` product supports a repository operator or implementation partner that must move scholarly records, preserve staff decisions and hand over a working service. It is an existing foundation for a selected SCF customer installation. The application retains its shared **$38,000, 400-hour, 150-day** programme; the six funded packages pay for remaining customer integration and deployment.

The [installed operating guide](OPERATING.md) gives the complete browser and command-line journey. The [original OAI application](../../stellar/scf-starforge-20261009/sf30-seller-sdk/oai-pmh/README.md) receives source responses, constructs reviewed editions and retains the original working history. The selected distribution includes the whole `products/tind` directory, both applications and their existing runtime components.

## The customer task

A library, university or repository implementation partner needs an agreed source collection to remain usable after migration. A successful delivery preserves distinct articles and complete issues; ordered contributors and their affiliations; source identifiers and existing DOIs; access and release terms; original files and external links; and later staff changes in the destination. Another engineer must be able to reopen the work, correct a record, receive a later source edition and continue support.

|Role|Responsibility in the installation|
|---|---|
|Commissioning customer or prime|Select the actual collection, receiving application, acceptance task, implementation fee and included corrections.|
|Repository authority|Define metadata reuse, file acquisition and redistribution rights, access decisions, source changes and withdrawals.|
|Merchant operator|Publish the agreed metadata service, resource terms, price, deployment and recovery responsibilities.|
|Independent buyer operator|Approve the complete requested output and cost, receive it in the actual application and accept or return concrete issues.|
|Receiving engineer|Restore the original workspace, operate a source change, reconcile native edits and retain the complete handover.|
|Destination administrator|Provide the selected institution's native configuration and perform or authorize changes to its repository.|

Commercial implementation and care are recorded in the original workorder, including named responsibilities, dated milestones, acceptance, support effort and actual collections. Grant-funded reusable changes and commercial work receive separate assignments in the existing delivery plan.

## Operate the complete installation

1. **Receive the source.** Use the original HTTP acquisition or import the original returned response with its retained acquisition information. Resume the same operation after interruption. The OAI workspace retains original XML, request identity, coverage and continuation.
2. **Select an edition.** Review the complete journal harvest or the explicitly selected GetRecord collection. Build the dataset from that selected source edition. Source coverage remains visible in the resulting customer output.
3. **Prepare the scholarly records.** Open the same workspace in TIND. Import the source cases, review ordered fields and people, edit the access and hierarchy decisions and retain each decision's source basis.
4. **Receive the destination.** Select the actual institution and receive its native MARCXML export. Reconcile existing DOI and OAI identifiers. Compare the last delivered source, current source and current native record so later source changes preserve unrelated staff edits.
5. **Acquire originals and organize production.** Review each original document URL, file role and access terms. Receive its actual returned bytes or resume the same streaming download, verify the retained file and adopt it into the original record. Save a production plan for explicit source collections, with an exact edition and record membership. It keeps already received and excluded records in its census, separates unresolved or deferred exceptions and groups the remaining work into reviewed waves.
6. **Prepare and receive native work.** Review changes against each wave’s saved source and staff decisions. Prepare all ready members or explicitly retain unresolved exceptions. Open the original native batch, receive actual record/file outcomes and reconcile the current destination export. A confirmed withdrawal remains complete when its target has been removed. Each prepared batch and later decision stays attached to its wave.
7. **Continue customer use.** Receive the next useful source edition or approved query through the same original application. Keep prior source, payment, delivery and review history available while applying new work.
8. **Hand over the installation.** Export the complete editable workspace, source-file cache, saved production plans and customer outputs. Export a plan’s full member census with its decisions and original batch history when the customer needs a standalone production register. The receiving engineer restores it, reopens the same records and decisions, performs the agreed correction or later source change and records the actual support outcome.

After installation, an existing original repository workspace opens with:

```sh
starforge tind-migration --python /absolute/python --workspace /private/repository serve --port 8894
```

The OAI and TIND applications use the same workspace lease. Close one before opening the other. Keep the full private launch URL with the selected operator. The operating guide covers installation, native configuration, record changes, batch receiving, files and complete recovery.

The original MSU driver receives either `--edition-mode staff-cases` for the 11-record collection or the default complete 15-record Endeavors edition. Use distinct output directories with the same original workspace. Its saved source, build, mapped decisions, MARCXML, operator capture and handover remain part of that receiving operation; append the native operator's actual execution and receiving result to the same case.

For a commissioning task that also needs cross-source identity review, select the maintained [record-mastering contribution](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/f8f27083267ca88af81bc7fe0b8a9414cc8b0e8f/stellar/scf-starforge-20261009/sf30-seller-sdk/record-mastering/README.md) alongside the repository product. Import the agreed flat CSV fields with stable original record keys, review suggested matches, explicitly merge or split records, and choose original or custom field values. Its immutable CSV, schema and field-provenance edition can feed the original dataset merchant; its complete private project reopens independently for later review. Keep this reviewed derivative linked to the original OAI edition and retain ordered MARC fields, article/issue distinctions and access decisions in the repository workspace.

## A recurring service with a useful purchased result

The commissioning work establishes the institution's source, mapping and receiving workflow. Recurring service then supports real new work: a newly published journal edition, changed access or contributor metadata, a requested metadata query, or a comparison between agreed source periods.

|Service unit|Customer output|Basis for later use|
|---|---|---|
|Reviewed metadata edition|The agreed complete collection, source coverage, original identifiers, reviewed mapping and usable export.|A new source edition or an accepted correction requested by the customer.|
|Approved metadata query|The requested population and fields, complete agreed pages, original source edition and receiving record.|A distinct useful query or period needed by the buyer's workflow.|
|Source-change comparison|The compared editions, changed records, preserved staff decisions and resolved receiving issues.|A real source update or a later destination review.|

The merchant advertises the exact priced HTTP or MCP resource. The buyer reviews the complete operation and aggregate cost, including every required page, before approval. The installed signer, facilitator, merchant and receiving application join the original request to the observed Stellar transfer and usable output. The institution's native administrative changes retain their own authorization and outcome.

A source's publication cadence governs useful recurrence. A monthly issue supports a monthly edition; additional purchases require distinct useful work. Replay recovers the original operation and retains its financial history. The cohort records completed tasks and purchases according to the shared application definitions, including complete accepted output and the original attempt time.

Implementation and care can fund mapping, installation, training, agreed corrections and ongoing support. A priced data resource funds the separately defined delivered result. The workorder records these service units, actual fees and collections, included support and remaining effort so one completed activity is assigned once.
