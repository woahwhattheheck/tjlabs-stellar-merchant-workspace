## Municipal asset migration and target receiving

### Customer problem and installed product

A municipality or its implementation partner needs to carry an existing asset inventory into a new system while keeping the relationships that make it useful: source objects, asset and location identifiers, service requests, work orders, observed geometry and returned changes. A useful migration handover also needs the original files, explicit mapping decisions, unresolved exceptions and enough saved state for another operator to continue the work.

The installed municipal asset application provides that workflow in the existing Starforge Applications and merchant tool surfaces. It adopts the maintained McPherson/Belleville operator and its original acceptance checker, complete public-source capture and refresh, and the Maximo target receiving extension. It complements the existing Open311 service desks with inventory migration, target comparison and editable project receiving.

The [complete operating guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/acf925fb324e29bc40b46c05eef38c37fa4f1f58/products/municipal-assets/OPERATING.md) defines the installed commands and operator journey. The [selected source manifest](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/acf925fb324e29bc40b46c05eef38c37fa4f1f58/stellar/scf-starforge-20261009/sf30-seller-sdk/municipal-assets/SOURCE_ADOPTION.json) retains every included source file and the original donor and addon identities. Application adoption keeps the original SQLite writer, expected project revision, named operator and request replay.

### Source identity and recurring public acquisition

The existing Belleville source provides a concrete complete public inventory: 2,262 source-qualified objects, ten typed attributes and an observed geometry edition containing 2,296 paths and 14,821 coordinate positions. Its acquisition and mapping remain in the original municipal case. The installed application includes the generic source readers and repeatable refresh; the actual private case and captured files stay in that authorized customer workspace.

OBJECTID is qualified by its actual source layer. Repeating asset, municipal and segment identifiers remain original attributes or explicit mapping choices. Null values, literal whitespace and numeric values survive source intake. Geometry retains the provider's observed coordinate reference and original output edition. A later geometry observation is not described as physical movement merely because the earlier source lacked coordinates.

The complete refresh keeps actual provider responses, before/after metadata and IDs, original attribute and geometry pages, source reconciliation, retry state and complete outputs. A continued operation preserves the same project, actor, selected revision, mappings and source request. The comparison applies to those observed source editions; a stable ID list alone does not establish that every source value stayed unchanged throughout acquisition.

The received customer can reopen the prior full capture, source archive, report and editable project. A following intended refresh uses that project's current observed revision. Path-bound work already in flight continues at its original physical workspace; completed source files and editable project state travel in the full handover.

### Configured target receiving

The Maximo extension reads a configured tenant's actual schema and complete target collection. Native object identity and compound keys stay distinct from provider resource links and the mapped source identity. The operator reviews the original target fields and explicit mapping before preparing an Add or Update load.

Prepared loads retain their original selected source, schema, field mapping and exact request body. The prime's existing native dispatcher supplies the actual returned envelope. The application receives that complete original outcome, shows each row's returned result and retains its source context. The next complete target capture supplies the actual post-operation target observation.

Preparing a load is one stage of this workflow. External mutation and customer acceptance belong to their actual native results. The application does not infer installed tenant fields, invent acceptance references or turn a proposed repair into a completed provider update.
