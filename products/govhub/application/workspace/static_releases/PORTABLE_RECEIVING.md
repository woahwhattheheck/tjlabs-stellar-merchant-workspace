# Tome: complete portable native receiving

This programme receives one explicitly selected complete GovHub application and original Drupal runtime, operates native editorial editions and release recovery, opens both saved workspaces in the browser, and produces a complete private handover. It preserves the original runtime receiver, native command ownership and receiving history. Complete local packaging is the default; an existing authorized file publisher may be supplied explicitly afterward.

## 1. Select the complete inputs

Use the complete application ZIP generated by the public application builder, the actual finalized Drupal runtime archive and its full SHA-256, the original Tome 8.x-1.16 archive, and the native/browser programmes from that same application edition. Select an installed Node/Playwright/Chromium runtime and a private operation directory.

Create a private source-selection JSON with schema govhub.tome-portable-source-selection.v1. The required fields are:

| Field | Exact selected value |
| --- | --- |
| operation_id | One stable commissioning operation ID of 8–160 characters. |
| source_commit | Full commit from the selected APPLICATION_SOURCE.json. |
| application_manifest_sha256 | SHA-256 of that complete original source lock. |
| source_files, zip_members | Actual counts returned by build_application.py verify. |
| application_zip | Object containing actual bytes and sha256 of the whole application ZIP. |
| tome_archive | Object containing actual bytes and sha256 of the unchanged Tome archive. |
| site_mail | Actual selected site administrator email. |
| pins | Complete source identity objects containing bytes and sha256 for builder, runtime_receiver, native, browser and browser_guide. |
| delivery_helpers | Optional original publisher-helper filename→SHA-256 map. |

The builder is application/workspace/build_application.py; native is run_tome_release.py; browser is run_tome_browser_receiving.mjs; browser_guide is BROWSER_RECEIVING.md. The runtime_receiver is the actual maintained drupal_runtime_handover.py inside the selected runtime archive. The receiver verifies its full bytes before importing it. Do not infer these identities from filenames or use a different programme on continuation.

If selecting an existing publisher, add its exact pins.delivery object and original helper hashes. Its library helper directory and delivery programme are explicit local inputs; no connector or new remote destination is created by this source.

## 2. Run the whole receiving command

All path arguments must be absolute. Select a new owned operation directory with room for the original runtime, its dedicated project, both workspace copies, browser downloads and the final ZIP. The receiver creates its own private directories and records the exact selection in `input.json`.

```sh
python3 -B -u /absolute/source/run_tome_portable_receiving.py \
  --source-selection /absolute/private/source-selection.json \
  --application-zip /absolute/inputs/GovHub_Application.zip \
  --runtime-archive /absolute/inputs/Original_Drupal_Runtime.tar.gz \
  --runtime-sha256 ACTUAL_PUBLISHED_RUNTIME_SHA256 \
  --tome-archive /absolute/inputs/tome-8.x-1.16.tar.gz \
  --directory /absolute/owned/tome-receiving \
  --browser /absolute/source/run_tome_browser_receiving.mjs \
  --browser-guide /absolute/source/BROWSER_RECEIVING.md \
  --guide /absolute/source/PORTABLE_RECEIVING.md \
  --node /absolute/existing/node \
  --playwright-module /absolute/existing/node_modules/playwright \
  --chromium /absolute/existing/chromium \
  --keep-open
```

The directory and files belong to this one operation. Its `.portable-receiving.lock` holds the original local writer through runtime receiving, native execution, browser inspection, packaging and publication.

Optional flags:

| Flag | Meaning |
| --- | --- |
| `--php /absolute/existing/php` | Select the receiving host's actual PHP8.3.6 executable. When omitted, the original runtime receiver selects the PHP included in its archive. |
| `--single-process` | Pass the existing browser companion's compact Chromium option on a host already using that browser mode. |
| `--delivery-programme` and `--library-helpers` | Supply both to continue an existing authorized original file publisher after complete local packaging. Their exact source identities must be in the same private source selection. |
| `--keep-open` | Keep the same programme alive after a native/source/browser failure so its original directory, logs and temporary allocation remain available for a deliberate continuation. Keep stdin open. |

Existing font and shared-library environment settings pass through unchanged. The receiver adds only its owned temporary directory, the original runtime's launcher directory to PATH, and Python's no-bytecode setting.

A process-private `/dev` allocation can hold the expanded runtime and final archive while that process remains alive. Files in such an allocation must reach the final saved result before that namespace closes. Choose a genuinely persistent host directory when recovery must survive the process itself.

## 3. What the command operates

### Receive and reopen the original runtime

The entrypoint first verifies the complete saved application with its original `build_application.py`, then extracts the exact selected bytes and checks `APPLICATION_SOURCE.json`.

It reads the complete runtime archive and verifies its whole SHA-256 before loading the archive's own `drupal_runtime_handover.py`. The original `receive(...)` routine performs the complete member verification and receiving, prepares the original project paths, observes PHP/Composer/Drush, and returns the actual project, document root, launcher directory and `NATIVE_RUNTIME.json`. It reopens a retained COMPLETE runtime receipt from the same receiving directory.

The returned project becomes this operation's dedicated site. The maintained `NativeDrupalSite` helper verifies that Drush and the site root belong to that same Composer project, retains original and materialized lock hashes, and stores the actual site binding and private receiver account. The site setup directory is separate from the project so the application's original source and backup capture retain their intended boundaries.

### Operate two real editorial editions

The original application programme `workspace/static_releases/examples/run_tome_release.py` performs the complete native sequence:

1. Prepare the dedicated site and install the original Tome source through the maintained native setup.
2. Apply editorial editionA, capture the actual generated output and receive it as an immutable static edition.
3. Create and read every page of the original complete path comparison; save the approval for that exact comparison.
4. Stage and publish through the original worker and target operations, then inspect the actual current release.
5. Apply editorial editionB and carry the same capture, complete review, stage, publication and target inspection.
6. Roll back to the retained predecessor and verify that the first edition is the current target again.
7. Export the original static handover, open its full member inventory, back up the original workspace, reopen the receiving workspace with its actual account and independently download the same handover bytes.

The whole source, target, edition, comparison and release identities remain in the original application. The wrapper saves `native-complete.json` only after the native result reports COMPLETE with the selected source commit and manifest hash.

### Open both original browser workspaces

The maintained browser programme starts the original GovHub server in the same living context, signs into its actual account and exercises the installed static-release views. It reads every inventory/comparison page, uses the query/change controls, opens the retained native capture/stage/publish/rollback records, and downloads generated output from both editions plus the full handover.

It then opens the independently received workspace and repeats the same operator views. The programme inspects desktop1366px and mobile390px, retains its screenshots and complete route responses, and closes each original server before proceeding. The receiving command accepts only the original browser COMPLETE result with both workspace runs.

For the exact browser API and standalone browser continuation, read the retained `source/BROWSER_RECEIVING.md` and the selected `run_tome_browser_receiving.mjs`. The wrapper uses this complete companion directly.

## 4. Complete operating output

The final delivery saves six artifacts, in this order:

| Output | Purpose |
| --- | --- |
| `delivery/GovHub-Tome-Native-Receiving.zip` | Whole private operating handover: source, selected application ZIP and Tome archive, both native workspaces, the static target tree, native handover, original request/results, and complete browser outputs. |
| `delivery/PACKAGE.json` | Every member's exact name, type, mode, byte count and SHA-256, plus application/runtime/native/browser identities. |
| `delivery/NATIVE_RECEIVING.json` | Complete joined native/browser result, final ZIP identity and manifest identity. |
| `native/delivery/GovHub-Tome-Native-Result.json` | Original application's site UUID, source/target/edition/release identities, static handover and independently reopened download. |
| `browser/GovHub-Tome-Browser-Receiving.json` | Original two-workspace browser result and complete physical output map. |
| `source/PORTABLE_RECEIVING.md` | This complete operating guide; the ZIP also presents it at its root as `START_HERE.md`. |

The wrapper copies all selected receiving programme sources into `source/`, including the exact original runtime receiver, native browser companion and its whole guide, and retained transfer programme. The application ZIP itself supplies its complete builder, native caller, service/UI and native setup source.

The final ZIP preserves each original relative release pointer as an actual ZIP symbolic-link member. Its manifest records the literal target, kind, bytes and hash. The receiver accepts these pointers only when their resolved destinations stay inside the retained native/browser/source trees; it does not follow them to copy another workspace. Ordinary files are streamed into the archive, and every member plus the whole ZIP is independently reopened and checked before publication.

The expanded dependency runtime remains in `runtime/` on the host. Its original complete archive is a separate pinned receiving input. Keep that saved runtime archive with the final handover when another host needs to operate the dedicated site.

The complete operating ZIP contains the private receiving accounts and workspace state needed for this internal handover. Keep it in the existing authorized custody. Keep the public application-only source separate from this private editable project archive.

## 5. Read progress and continue the same operation

The programme emits a small JSON stage at useful boundaries. Detailed original command output stays in its owned `commands/` files.

| Observation | Original retained authority |
| --- | --- |
| Application extracted | `application-receiving.json`: original full builder result and manifest identity. |
| Runtime received | `runtime-receiving.json` plus `runtime/RECEIVING.json`: original archive, actual dedicated project, native version observations and relocation records. |
| Native command returned | `commands/original-tome-native-NNNN.json`, its stdout/stderr, and the original native operation's own request/result records. |
| Native complete | `native-complete.json` binds the original native result to the whole selected input. |
| Browser command returned | `commands/original-tome-browser-NNNN.json`, its stdout/stderr, and `browser/GovHub-Tome-Browser-Receiving.json`. |
| Package ready | `TOME_NATIVE_PACKAGE_READY` lists all six exact completed files. |
| Files saved | `publication.json` contains the unchanged ordered provider results and actual file identities. A COMPLETE result requires all six original file saves to succeed. |

When `--keep-open` reports `TOME_ORIGINAL_HOST_RETAINED`, use one JSON command per line on that same process:

```json
{"action":"status"}
```

This returns the saved failure location and reason. After correcting the actual source/runtime condition while preserving the same selected input and completed records:

```json
{"action":"continue"}
```

`continue` re-enters the same operation. Exact application/source files must still match. The original runtime receiver reopens its COMPLETE receipt. If `native-complete.json` already exists, the wrapper checks and reuses that native result, then continues the browser/package stages. The existing browser companion handles its own exact COMPLETE result reuse. A completed `publication.json` returns the saved provider results after checking every artifact's retained identity.

`{"action":"exit"}` ends a retained failure context. On a process-private host, first preserve every artifact and original transfer record that is still needed.

### Continue an explicitly selected file transfer

Without a delivery programme the command returns COMPLETE with the full local file identities and publication:null. Preserve those completed files in the selected durable custody. The following remote-publisher continuation applies only when both original publisher inputs were explicitly supplied.

The final file save delegates to the maintained `LibraryUploadWorkflow` through its already operated `RetainedFileTransfer` adapter. It preserves the exact prepare replies, transfer state and original provider results below `save/`.

If the programme reports `TOME_PORTABLE_TRANSFER_RETAINED`, it keeps the original transfer instance in the same process. Use:

```json
{"action":"status"}
```

or, after the existing result identifies the original unfinished transfers:

```json
{"action":"resume-original"}
```

This continues the original unsuccessful reservations through the original transfer adapter. It does not allocate a replacement set. A prior STARTED or PARTIAL publication from a closed process must be reconciled from `publication.json` and `save/` before a further save is selected; changing the label or destination does not erase that request.

The retained input includes all programme paths, complete source hashes, runtime/application/Tome identities and browser selection. A deliberate source successor should retain the previous operation's completed records and be composed explicitly. Do not overwrite `input.json` to make a changed programme appear to be the original selection.

## 6. Open the completed handover on another host

Start with `START_HERE.md`, `PACKAGE.json` and `NATIVE_RECEIVING.json`. Verify the package's complete hash and member inventory before restoring its actual relative release links. Use an extraction method that preserves the manifest's UNIX file/link types and rejects entries escaping the selected receiving root.

The original static handover is available at `native/delivery/Static_Release_Handover.zip`; the separately downloaded receiving copy is `Static_Release_Independent_Receiving.zip`. Their exact byte identity is recorded by the original application. The full received GovHub workspace is `native/receiving-workspace/`, and the original workspace and all application source bindings are recorded in the native result.

Use the unchanged original GovHub server and its actual workspace/source/assessment-core arguments to inspect that workspace. The selected source package unpacks as `govhub-operations/`; the full original browser guide documents its server command and account location. Absolute native target locations remain part of the original operating records. For a deliberately different host target, use the application's original target configuration, review and operation workflow to establish the new target.

To establish a fresh dedicated native site, use the original saved runtime archive and the whole command above in a new owned receiving directory. Retain the prior completed handover as the source operating edition. The original producer, installed runtime receiver and native GovHub application remain the maintained engines for that continuation.

## 7. Source identity and rendered receiving

The private source-selection JSON, original application manifest and every native command/source hash identify this complete operation. The public source migration manifest identifies the generic implementation; it is not a native completion receipt.

Open the exact outgoing application and complete handover at wide and narrow widths, actually view the captured images, use the original controls, and reopen each downloadable archive/report with the recipient's original account. Source review, HTTP success or DOM counts do not replace this inspection. Correct observed layout or receiving problems in the same operation. When the equipped runtime is unavailable, retain the full current source and original pending operation for its existing owner; do not claim native or rendered acceptance.
