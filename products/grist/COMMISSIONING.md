# Grist customer commissioning and independent workspace receiving

This course takes the existing Grist customer implementation from its actual document/table selection through reviewed data delivery, complete editable workspace handover, and continued customer operation. It uses the original Grist source workspace, publisher, SF82 release store, Applications and merchant MCP. The complete workspace file preserves the selected workspace’s saved source and operating history so a recipient can receive a separately named, editable copy through the maintained product.

The original commercial case is **grist-customer-integration-workshare-20261012-14f5**. Its proposal covers one Grist document and up to two named user tables, with separate workspaces, reviews and outputs for the tables. It includes two review rounds and a 90-minute handover. The source enhancement does not change those proposed terms or create another customer contact.

Use the complete selected product revision and its current [source workspace guide](../../stellar/scf-starforge-20261009/sf30-seller-sdk/grist/WORKSPACE.md), [whole workspace handover guide](../../stellar/scf-starforge-20261009/sf30-seller-sdk/grist/HANDOVER.md), [original receiving course](../../stellar/scf-starforge-20261009/sf30-seller-sdk/grist/RECEIVING.md), and [Operating Plans guide](../../stellar/scf-starforge-20261009/sf30-seller-sdk/grist/OPERATING_PLANS.md). The source directory is stellar/scf-starforge-20261009/sf30-seller-sdk/grist. The original installed entry is **grist-workspace**; there is no separate grist-project wrapper in this course.

## 2. Keep source, release and recipient identities distinct

The product has several kinds of identity, each with a different job.

| Identity | Why it matters in handover |
| --- | --- |
| Native document/table/field | Defines the source the declared account actually read. |
| Document catalog and discovery UUIDs | Bind the selected table and visible native schema to the actual retained observations. |
| Capture manifest and resource hashes | Identify the complete original typed responses and their surrounding metadata. |
| Draft revision | Guards the current editable field projection. |
| Source version | Identifies a reviewer-bound, immutable projection over that retained capture. |
| Publisher plan/candidate/review/publication | Retains the original publication decision and generated dataset. Numeric plan IDs are distinct from folder UUIDs. |

| Receive request, child name and returned workspace identity | Identify the recipient’s separately placed editable workspace. |
| Browser working editor | Retains unsaved local work independently of the native saved project. |

Record actual returned identities, rather than assigning numbers from examples. A lost response does not create a new intended operation: reconcile the original UUID and exact input through the product’s saved receipt and recovery controls.

## 4. Select real metadata, then capture the actual table

In **Capture source**, choose the declared connection and enter the exact document ID. **List document tables** retains the actual document metadata and native table catalog. Page and search that retained catalog, choose the actual table, then **Inspect actual metadata**. Catalog navigation itself performs no new source read.

A catalog binds the document, connection and original read authority. A different credential or host connection calls for a new explicit metadata observation. The table listing establishes visible metadata; subsequent discovery and capture establish the actual selected fields and rows.

Choose the native record order, complete field/type union and public projection deliberately. Preserve the source filter, selected account and actual discovery/catalog identity with the captured source. The model retains the whole original observation even when a concurrent draft edit prevents that capture from replacing the newer draft.

### The eight original resources

A completed capture retains:

1. Document metadata before.
2. Recent document history state before.
3. Visible native column metadata before.
4. One complete typed records response.
5. A second complete typed records response.
6. Visible native column metadata after.
7. Recent document history state after.
8. Document metadata after.

The two complete record responses must match byte for byte. Visible schema and the observed document history head, including its native action number and hash, must agree around the reads. The original request URLs, receive times, permitted response headers and complete body bytes travel with the capture.

This is an observed consistency check over API-visible data. The saved manifest keeps **documentStateVerified=true**, **repeatReadVerified=true**, **countVerified=false** and **atomicSourceSnapshot=false**. The row count is derived from the complete returned records; it is not an independent database count. The history endpoint may be pruned. A captured table is not every historical document revision, an unrestricted account export or an atomic snapshot of all tables.

The current original native programme is **SCF-GRIST-PUBLIC-SOURCE-20261012-14F5**, using the official Task Management candidate **hik1whAV5snj**. Select its real returned table and field IDs when the original acquisition completes. Do not manufacture a table name, row count or successful capture from that public example’s presentation.

### Source refresh and interruptions

A new capture is an explicit action. Opening, receiving, inspecting a saved edition or opening Operating Plans does not refresh Grist. Resume an interrupted provider read with its original request, declared source bounds, credential binding and step journal. Matching complete staged response receipts can be reused. A changed source/head/schema/read authority remains a distinct observation.

A source mismatch or changed record body should produce its real retained failure and a reviewed new capture. Do not rewrite the saved source hash, silently omit records or call a partial response a complete table. Honor the provider’s actual retry interval.

## 5. Review native value meaning before publication

Grist typed API values require explicit handling. Keep the original native type, representation and field identity in the staff review. The same interpretation must survive source export, full workspace receiving and later publication.

| Native value or condition | Supported decision |
| --- | --- |
| Record ID | Use the original $recordId projection and identity-text when a public string identity is needed. |
| Int or Numeric | Preserve the original JSON number token through number-text, or choose a supported native number only when the full value passes the lossless finite/safe round-trip check. |
| Numeric-looking text | Keep it as text. number-text requires an actual native JSON number token. |
| Date | epoch-seconds-text preserves the original Date tuple’s seconds token. Any calendar conversion is a separate explicit consumer decision. |
| DateTime | Retain the complete declared timezone and matching typed tuple. epoch-seconds-text does not silently convert to a new timezone. |
| Ref | reference-id-text preserves the native referenced row ID, including the original empty-reference ID 0. It does not look up a display name. |
| Lists, objects, RefList and Attachments | Use the supported typed-json representation with recursive native code validation. IDs do not retrieve linked rows or attachment file bytes. |
| Missing selected field | Treat it as missing access/data; it is not null. |
| Actual retained null | Apply the explicit nullable rule. |
| Empty string | Select empty-to-null deliberately, or a representation that preserves an empty non-nullable string. |
| Censored, error, pending, skipped, conflicting, unknown or unserializable typed value | Correct or omit the selected field explicitly. Recursive validation prevents hiding these as null or harmless text. |

The original CSV output represents null as an empty field. A nullable string with empty-preserve is ambiguous and is rejected by the original validation; do not remove that protection during commissioning. Grist itself may normalize a native null list to an empty list in its API response. The product preserves the validated API representation and does not reconstruct undocumented raw database cells.

Inspect the entire projected result with **Validate every row**, not just the browser’s displayed preview rows. The original browser shows a limited preview for usability; the underlying validation covers every retained row for every configured query. Source record order, preview order and final publication order are separately recorded choices.

Record a compact field decision sheet with native ID/type, alias, output type, encoding, nullable, empty policy, example interpretation and staff decision. Use actual customer fields and actual source values. Do not insert fixture values into the original source as evidence.

## 7. Continue the existing Operating Plans workflow

Use **Operating plans** in the same source workspace to turn retained work into a practical staff procedure. It shares the original authenticated service, source database, source owner and request journal. It does not create a second server or trigger provider extraction, publication or payment.

A procedure can bind retained document catalogs, discoveries, complete captures, source versions or original operations. It can also begin as a manual procedure with no native selection. Use its real customer outcome, staff owner, recurrence, steps, inputs, expected results, due dates and recorded progress. Preserve each stable step ID.

The procedure’s origin is tied to the original raw workspace settings identity. Whole receiving preserves that logical identity and places runtime files through the maintained placement layer. Do not “repair” a received procedure by replacing its origin with a new directory hash. Native procedure validation and returned-plan review remain the original implementation.

### Saved native work and unsaved browser work

The whole workspace file carries the **saved** Operating Plans database records, revisions, bindings, retained observations, applied returns and request history inside the original sources.sqlite. It does not take an invisible snapshot of unsaved browser local storage.

Before preparing the workspace file:

- Save each intended procedure revision through **Save procedure revision**, preserving its current version guard. Save desired source-projection edits through the source editor, or deliberately reload the saved source draft; that editor has no separate complete working-copy download.
- Use **Download complete working editor** for any unsaved draft, incomplete custom JSON, returned file, pending request or other browser-only work.
- Keep the full editor backup as recovery for its original workspace. The current browser importer validates both the exact original directory and origin, so preserving the settings identity does not make this unsaved backup importable into a differently placed child. To carry desired procedure edits into the received copy, save them in the original native procedure before exporting .grwh.
- Preserve existing complete procedure JSON and original plan JSON where the customer needs their independent editable procedure handover.

Within that original workspace, the existing panel can list/open saved editors as separate local copies, open a complete working editor, retain the prior full editor, and recover a pending exact request. Reopening a newer saved procedure does not silently rebase an older dirty editor.

The complete procedure export carries authored history, source bindings, observations and return records. Readable Markdown/HTML are useful staff views. The editable JSON is the authoritative companion for later procedure editing and return. Attached step files remain part of the original working/returned plan formats.

### Returning a procedure after independent receiving

An independent received workspace may continue its saved procedures. To return procedure work to the author, use the existing Operating Plans course:

1. Export the complete saved procedure or original generic operating plan from the recipient’s original panel.
2. Keep the author’s current procedure and unsaved draft intact.
3. Use **Receive unchanged forward history** only when the shared history is identical.
4. For divergent work, use **Compare returned work** and inspect the shared/current/returned complete values.
5. Review conflicts with **Keep current**, **Take returned**, **Use shared original** or the supported complete custom JSON value.
6. Recompute the comparison after changing choices. Preserve exact ordering and grouped instruction/progress/file decisions.
7. Use **Apply this complete reviewed return** only for the matching current procedure and actual ready comparison.
8. Retain the full saved procedure and applied review after reopening.

The complete workspace receiving feature does not replace this original return engine, merge a customer branch into the author’s source draft or select a new publication. The existing Operating Plan authors and original customer procedure custody remain unchanged.

## 9. Prepare one immutable complete workspace file

Save intended source and procedure edits first. The source editor requires saving or deliberately reloading its saved draft. Download any unfinished procedure editor as recovery for its original directory/origin; it is not a portable unsaved-editor import into the new child. Read the actual current draft revision and selected source version; selection is null only before the first version.

A genuinely stale expected draft or selected version is rejected. After success, the saved export receipt identifies the immutable file, size, complete SHA256, manifest SHA256, source and retained counts. Read that receipt; do not infer the file from a directory name.

Use **Download complete workspace**. The original ticket/stream download avoids loading the full file into a browser JSON response. Retain the actual complete bytes and receipt through the approved private transfer route.

The archive supports up to **32 GiB of content plus 32 MiB of manifest and the 13-byte header**: **34,393,292,813 total bytes** at the configured maximum. Uploads use **1 MiB** chunks. A completed export request is immutable. Reopening or downloading that saved file returns its original receipt. If services have since been reopened, replaying that already completed export does not stop them again or silently create a new snapshot. To export a later genuinely edited workspace, use a new deliberate request with its new current source basis.
