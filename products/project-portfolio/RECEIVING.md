# Installation and customer receiving

## Build the selected product

The project-portfolio contribution owns the complete source component, customer
commands, typed client, Applications adapter and merchant provider. The selection
recipe includes the maintained runtime installation, Applications and MCP support.

Build from a complete immutable checkout with the original distribution builder:

~~~sh
node stellar/scf-starforge-20261009/distribution/build.mjs --repo /absolute/checkout --ref COMMIT --out /absolute/release --offline --selection project-portfolio
~~~

Keep the complete built package and its manifest. Use the maintained installation
and runtime-profile workflow to select the actual runtime dependencies, then
install the selected Python requirements. The original runtime command reports
MPXJ 16.10.0, JPype1 1.6.0, the actual JVM and its complete JAR identities.

All 63 original source files are selected by SOURCE_ADOPTION.json. The installed
host verifies them together with its launcher, command line, typed client,
Applications adapter and merchant interfaces. The original source directory is
included in full, including the browser assets, native receiving programmes,
examples, source references and license.

## Receive the installed application

Use the complete installed receiving programme against the original workspace.
An existing workspace retains its actual editions and requests. Supplying an
original project file also exercises the complete authenticated upload, download
and hash verification path.

~~~sh
project-portfolio-receive --workspace /absolute/projects/portfolio --directory /absolute/receiving/installed --python /absolute/python-environment/bin/python --original-file /absolute/source/Engineering.mpp
~~~

The programme opens the actual original application, pages its existing editions,
transfers the selected original file, creates or reuses one stable full-workspace
archive request, downloads that archive through the customer client and merchant
provider, releases and resumes the full-file reader, stops the application and
reopens its same workspace with a fresh local authorization. It then reads the
same saved request and original editions.

The complete result and downloaded files remain in the selected receiving
directory. The programme uses its original stable archive request when continued.
A saved result reopens its exact retained files; an unfinished agent file verifies
its existing prefix against the original export before continuing.

This programme verifies installed operation and receiving. Native project parsing,
native writer roundtrips, target operations and reporting calculations are covered
by the original source programmes below using their selected actual input.

## Continue the original native receiving

The complete original product includes three native receiving programmes:

| Programme | Source path | Actual input |
| --- | --- | --- |
| Source engine | source/native_receiving.py | Original pinned MPXJ fixtures, installed MPXJ/JPype/JVM and the original source receiving directory |
| Migration operator | source/operator/native/receive.py | Original project input, target profile and retained operator workspace |
| Reporting archive | source/archive/native/receive.py | The actual completed original workspace and original edition IDs |

Use each programme's original README and arguments. Retain the same native
operation directory when continuing an interrupted run. The source programme
returns source_workspace and the actual sources[].edition_id values consumed by
the subsequent archive programme.

The upstream fixture identity is MPXJ commit
7ef9e72813d33378c55ec6ceb148cc831ed22033. The complete original source and fixture
bundle are retained in the public source publication recorded by
SOURCE_ADOPTION.json. Its native-input carrier and receiver preserve the exact
source and fixture bytes. The native programmes use the original engine's actual
fields, calendars, costs, timephased values, corrections and output files.

## Customer package contents

Deliver the complete installed product and its manifest, the selected runtime
profile, the actual workspace or reporting archive, full original result files
and these operating guides. Keep the receiving result with the original request
and source identities.

The host connection and target credentials remain in their separate private host
directory. Open the received workspace on the receiving host to create its local
connection. Reconfigure the host file aliases and actual target profile against
that workspace when continuing agent or target operations.

## Managed release source

Applications reviews the installed runtime source, then opens the original
application from its managed release. The prepared command retains the original
source directory and selection hash. Before opening, both launchers check every
selected original file and the corresponding file in the executing release.
Moving or updating either source requires a new application preparation.

## Native period receiving

The original reporting receiver accepts `--native-timephased` when continuing
the completed original source workspace. It uses the same edition IDs, the exact
native MPXJ fixtures and the original reporting operation. That phase retains
actual native period captures, published tables, complete reporting archives and
the receiving workspace. Follow [the original native receiving
instructions](source/archive/native/README.md) for its exact input arguments.

## Source adoption and future updates

SOURCE_ADOPTION.json identifies the original source commit and each exact file.
Updates to the source/operator/archive product are adopted as a complete new source
cohort. Existing workspaces retain their original editions, requests, archive
manifests and target history. Review the changed installed source and target
configuration through the existing Applications flow before starting the updated
runtime.
