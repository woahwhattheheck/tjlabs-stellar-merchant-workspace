# Buyer demonstration: receive useful output, then hand it over

Use the existing **Grant purchase reviewer** to answer a practical buyer question: “Can I understand what was purchased, read every byte I received, and give the same usable result to my receiving engineer?”

This is an operator-led course for the already retained purchase. It uses the original historical source, quote records, native transfer and complete result. It does not make another purchase, refresh the source or create a new adoption observation. The suggested sequence below is a presentation plan; actual completion remains in the existing workbench's action history.

## Select the original product

Use the existing reviewed Runtime with native Stellar packages, MCP and operator support. Preserve its selected source archive, complete lock and READY installation. The host operator selects an owned private parent directory; each receiving operator uses its own private workbench.

In **Applications**, choose **Grant purchase reviewer**. Select that Runtime and the private workbench directory. Leave Packet and SHA-256 empty for the bundled original, then choose **Review → Save → Connect → Start → Open**.

The installed CLI opens the same product:

~~~sh
starforge grant-demo workbench --dir /srv/starforge/state/grant-review --port 0
~~~

These example paths must be replaced with the actual operator-owned directories. For an already selected source checkout, replace `starforge grant-demo` with `node stellar/scf_2026/presentation/reviewer/cli.mjs`. Use the actual startup address and instance. Access codes remain in their original private connection; they do not travel in the packet or presentation.

|2. Review scope before results|Open **Source and query** and its complete source-document downloads.|What population, historical source vintage, query and terms does this output represent? Explain the retained truncation flag before presenting any row count.|
|3. Receive the original files|Choose **Receive this packet**, then **Open original Buyer → Buyer results**.|Does the customer have the complete source-linked result? The receiver restores the original records and complete files.|
|4. Read the entire result|Select the primary quote and choose **Read complete saved result**. Read or download all retained ranges.|The bundled response contains 100 building-in-project rows, 14 columns and 53,468 bytes. The original Buyer verifies the complete byte count and SHA-256. Its truncation flag remains true; these historical events are not a current housing listing or the complete 144-row acquisition.|
|5. Explain the payment and exception|Inspect the primary confirmed seller/matched transfer, then separately select the earlier indeterminate quote and read its complete 4,733-byte error result.|Which outcome belongs to each original attempt? Retain the indeterminate observation and error separately; opening it does not change the successful quote's identity or charge again.|
|6. Produce the handover|Choose **Handover → Close Buyer and export packet**. Download the full packet and its displayed SHA-256.|Can the receiving engineer get all original transitions and files? Export waits for the original Buyer to drain and release its writer, then captures that closed view.|
|7. Receive independently|The receiving operator selects the packet and digest, its reviewed Runtime and a new private workbench. |8. Continue the actual customer conversation|Record the buyer's actual source, recurring task and receiving requirements in the existing Installation/workorder.|Which reporting period, query or refresh would this buyer purchase next, who pays for implementation/resources, and who accepts the result? The direct receiving command is:

~~~sh
starforge grant-demo workbench --dir /srv/starforge/state/received-review \
  --packet /srv/starforge/received/original-review.json \
  --sha256 ORIGINAL_EXPORTED_SHA256 --port 0
~~~

**Review receiving copy** performs the existing local-copy path and labels it accordingly. A local copy is useful for demonstration; it does not establish an independently operated merchant or buyer. **Reopen this received packet** reopens the original Buyer after a closed export.

## Convert interest into a concrete installation

Use the existing Installation fields and the customer's original workorder. The presenter asks for the actual authorized source and population/period, output and receiving application, advertised paid unit and aggregate cap, independent merchant/buyer, commissioning payer, host/cost owner, receiving engineer and acceptance owner. A named installation stays proposed until its actual agreement and selection support another state.

Select a recurring job from the customer's work: the next required report period, revised source edition or distinct useful query. Record the actual cadence and complete page/file need. Thirty purchases in fourteen days cannot be inferred from two buyers making one weekday purchase each. Keep useful customer tasks and distinct advertised paid requests separate; do not invent demand by replaying or splitting a result.

For a recurring-data buyer, the existing OData example supplies a complementary operated outcome: all 830 original Orders, typed collection, saved SQL, 21-country summary, report, two-sheet workbook and independent receiving. Its three subscription editions, original-request replay and publisher/customer restores demonstrate continuity; an unchanged source produced zero row changes. Open that operation's complete original packet using its existing guide and selected runtime. It remains a separate source/customer operation and does not add a paid purchase to this demonstration.

The installation's first approved testnet purchase and full output are T1 acceptance. Same-service two-facilitator use and the seven-day cohort are T2 work. Mainnet recurring use and independent production recovery are T3 work.

## Continue an interruption

Keep the same workbench, selected packet and original action IDs. Reconcile or repeat an interrupted action with identical input through the existing product. Recover an already published export by its original identity. A prepared managed start keeps its original request before child dispatch; reopen that controller rather than selecting a new workbench.

Applications **Stop** drains the workbench and its Buyer. The next reviewed Start reopens the retained workspace. Complete Open receipts describe their historical outcome separately from the current live Buyer. The source guide covers original console access and the existing merchant typed-client/CLI interfaces.
