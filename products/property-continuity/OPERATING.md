# Property continuity in the SCF workspace

Use this product to retain complete source and target editions, review the exact mappings between them, reconcile an actual load, record two rehearsals and the cutover outcome, and hand an independently editable case to the receiving team. The property, finance, document and spatial reviewers work in the same original application and history.

The SCF integration supplies a managed application, authenticated customer/agent access, a complete Installation profile and the original source chapter. The original Python application remains under **app/** with its own unchanged source selection. Its SQLite store, reconciliation engine, original requests, portable archives and browser remain the business implementation.

## 1. Choose the original case and source

Continue the customer’s existing Workshare and Customer installation. Record the accountable implementation partner, property and finance owners, document and spatial reviewers, original load writer, release authority and receiving engineer. Agree the actual source and target platforms, permitted extraction scope and complete migration cohorts before importing files.

The original Bluewave company operation and its commercial ownership remain in the existing company thread. Its qualification stage closed on 25 September 2026. The extracted document identifies the source context; a selected partner supplies its actual appointment, current contracts, platform field definitions and customer data.

The maintained product addresses the seven original data families:

| Family | Meaning to select and preserve |
| --- | --- |
| Property | Actual platform/namespace identity, parent identity and complete hierarchy coverage |
| Rental space | Original identity and its related property |
| Lease | Rental-space reference, explicitly declared LIVE/ACTIVE status, effective interval and end-boundary convention |
| Project | Original project identity, including separately maintained KPN references |
| Document | Controlled document identity, version, related property, actual file hash and byte length |
| Finance | Original financial authority, counterparty, exact decimal-text amount, sign convention and currency |
| Spatial | Original identity, coordinate reference system, units and retained coordinate meaning |

Source and target identities may live in different namespaces. A Docusign CLM document can refer to a Salesforce property when that relationship is explicitly declared. The workspace does not infer that similarly spelled identifiers belong to the same system.

Read [the full original operator guide](app/OPERATING.md) for field-level use and [the exact domain contract](app/CONTINUITY_DOMAIN.md) for accepted schemas and decision rules.

## 3. Create or reopen a physical workspace

A workspace has a portable UUID and a physical working directory. A received copy intentionally retains the portable UUID while having a different physical directory. Select both correctly whenever opening, editing, recovering a request or downloading a result.

For a new authorized workspace, choose one fixed UUID, original title and creation time. The installed command delegates creation to the original Python store:

~~~sh
starforge property-continuity create \
  --workspace /absolute/private/property-workspace \
  --id ORIGINAL_CANONICAL_UUID \
  --title "Selected customer property continuity" \
  --at ORIGINAL_CREATION_TIME_WITH_OFFSET
~~~

Replace each capitalized value with the actual selected value before execution. Reuse the same directory, identity and creation record after an interruption. Existing workspaces open from their original store and retained history.

Inspect the original binding before managed launch:

~~~sh
starforge property-continuity binding \
  --workspace /absolute/private/property-workspace \
  --python /absolute/python3 \
  --connection-file /absolute/private/property-workspace/property-continuity-connection.json \
  --receiving-directory /absolute/private/received-workspaces
~~~

The returned binding identifies the actual source, workspace and Python selection. Keep the private connection file in its authorized directory: it grants access to the local application. Link an operator to the application through the normal managed Open control instead of copying a capability-bearing URL into public reports.

## 4. Retain whole source and evidence

In **Sources**, import the complete original file and describe its origin. Select its actual platform, family and identity namespace, file format, source reference, acquisition time, expected row count, and complete or partial coverage. Preserve the original expected count even when the observed file differs; that mismatch is useful evidence.

Import the independent target extraction separately. Retain the original load UUID, input selection and digest, writer, actual start/completion, outcome and evidence. The target return must describe the actual loaded environment and its own extraction. Identical source and target bytes can be legitimate; the extraction and load evidence establish what each file represents.

Review every relevant source page. The UI exposes the original rows and original JSON number tokens with their pointers. Retained files preserve exact bytes. The source parser keeps long numeric tokens without rounding them through a binary floating-point value.

The local application’s declared bounds are:

| Item | Limit |
| --- | --- |
| One original file | 64 MiB |
| Distinct retained source and evidence bytes in one workspace | 256 MiB |
| One dataset | 25,000 rows |
| Source plus target rows in one reconciliation | 100,000 rows |
| Complete saved report | 64 MiB |
| Saved state | 8 MiB |
| Reconciliation pairs | 32 |

Agree complete cohorts for a larger estate before import. Include the related property population necessary for the selected hierarchy and other relationships. A partial cohort remains explicitly partial; absence outside its coverage cannot establish a lost row.

## 5. Review mappings and meaning

In **Mappings**, define the selected source and target columns, typed comparisons, identity and relationship roles. Review the whole mapping and retain its actual reviewer, reason and evidence.

Use actual identity namespaces for both sides and for referenced entities. Keep property hierarchy and rental-space references complete. A document’s property reference may deliberately target another platform’s property namespace. Project identity and KPN remain distinct where the original source defines them separately.

For money, use exact decimal text and a separate currency field. Preserve the finance source’s sign convention and authoritative system. Keep numeric source tokens distinct from text, customer objects and booleans. Numeric fields do not become dates or identity text merely because their displayed representation looks convenient.

For leases, select actual LIVE/ACTIVE status values and the interval convention. Effective dates alone do not declare that a lease is live. The reviewed inclusive or exclusive end boundary controls whether adjacent leases overlap.

For documents, retain the actual controlled version, full-file hash and byte count alongside the relationship. For spatial data, declare the original CRS, units and comparison meaning. The reviewer selects any customer-specific transformation in the actual upstream implementation; this local mapping does not infer a coordinate transformation.

Save changed mappings as new reviewed records. Earlier reports continue to identify their exact original mappings.

## 6. Run and inspect complete reconciliation

Select the source and target editions, approved mappings and actual load in **Reconciliations**. Run the complete selected cohort, then open the full report.

Inspect both-side totals and all row groups, duplicates, field differences and relationship findings. The report retains missing and extra rows when its declared complete coverage supports that conclusion. Where valid key coverage or completeness is unavailable, the affected conclusion is **UNVERIFIED**, with its coverage finding retained.

Use the complete JSON download for the full report. The visible report and finding pages are navigation over that complete result. Inspect the original numeric tokens when a difference involves a high-precision JSON number; the displayed token and pointer connect the comparison to the actual original file.

For each finding, record the accountable reviewer’s **REQUIRE_CORRECTION** or **ACCEPT_EXCEPTION** disposition, with its reason and original evidence. An accepted exception records the review; it leaves the source observation intact. A corrected source or target arrives as a new retained edition and produces a new report.

A later review can change the current decision basis. The application retains both the original authorization basis and the current basis required for the selected next operation.

## 7. Operate two rehearsals

Record the first rehearsal against its actual reconciliation, source acquisitions and original load. Include the complete review decision, notes and evidence.

The second rehearsal uses later actual source acquisitions and its own load and independently acquired target return. Preserve the same declared population and mapping lineage required by the domain contract. Reconcile its entire cohort and review its own findings before recording the second rehearsal. Link it to the accepted first rehearsal.

The two rehearsals are useful operating records: they show that the team repeated the intended movement and review on later input. Two labels on the same earlier extraction do not establish that sequence.

## 8. Plan and record cutover

In **Cutovers**, choose the accepted first and second rehearsals, current reviewed basis, complete scope, named authority, cutoff, change window, delta procedure and rollback/recovery plan. Retain actual recovery-readiness evidence.

Record the original release authority before the actual production load. After the load, receive its actual final independent target extraction and run the cutover reconciliation. The acceptance path checks the selected complete cohort and mappings, current final decisions, original authority, cutoff and load chronology.

Record a rejected cutover when the load fails, is partial, remains running or has an unknown outcome. Use the actual failed-load observation and reason. Leave an unavailable operation UUID, input digest, start/completion or final reconciliation absent where the original observation does not supply it. The rejected outcome remains a useful operational record, including when the planned window has passed.

Successful recovery or a following authorized attempt continues through its own actual retained observations. Preserve the earlier failed record and original evidence.

## 9. Export, receive and continue the same case

In **Workspace transfer**, export the selected saved revision and download its complete archive. The archive carries original source files, command inputs, first results, saved revision history, publications and selected application source.

Receive that original archive into an independent destination. Keep the archive’s full hash, length and original receive identity with its result. Open the returned physical directory, confirm the portable workspace identity and saved revision, and inspect the original sources, reports and history.

Perform a legitimate later edit in the receiving branch, save it, reopen the branch and export its continuation. The original branch remains available. A repeated original receive into the same destination must preserve that receiver’s later saved edits.

Browser drafts, saved requests, upload resumptions, reports and downloads are bound to the portable identity and physical directory. Select the matching original or receiving branch before continuing a saved request. A similarly titled workspace is insufficient.

In **Handovers**, record the actual receiving person/team, receiving and independent reopen times, correction/return reference and evidence against the accepted cutover. Keep the archive transfer record separate from any customer’s actual operational acceptance.
