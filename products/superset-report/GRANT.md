# Superset report commissioning and customer-agent operation

The Superset report product turns an existing authorised report into a maintained customer service: retain the original result and its meaning, review the selected edition, publish it through the existing Stellar merchant, complete the original buyer acquisition and transfer the editable project to the next operator. The browser, command line and customer-agent interface use the same original SQLite workspace and native dataset, publisher and buyer engines.

## The customer job

Agree one useful recurring report with the commissioning customer before installing its production service. Examples include a monthly operational view, a selected programme report or a time-bounded customer extract from an existing saved chart. The workorder names the source owner, implementation payer, merchant, buyer, receiving engineer and support owner. It records the chart or dashboard, chosen query and fields, reporting population and period, explicit row key where available, permitted recipients, required output, freshness trigger and next useful edition.

The customer signs off the meaning of a complete result. A saved query's limit, offset and filters are part of that result. Its returned row count is not the population of the underlying database. Multiple native query results stay in the capture even when the customer selects one query for publication. An intentionally empty result, missing value or unchanged edition remains meaningful under the agreed report definition.

The distribution review also covers the source account's permissions, reuse rights and audience. Credential values remain on the configured host. A project handover supplies the source definitions and retained report material; another host supplies its own authorised runtime references for later live acquisition.

## Install one complete product

Build and retain the original `superset-report` selected package with its exact source commit, complete manifest and installed-runtime record. Follow the maintained operating guide for Node, Python, the original Superset provider and runtime dependencies. Managed Applications opens **Superset chart data** against the chosen private operator and report workspace.

The customer-agent setup belongs to that same installed product. Its private connection selects the actual workspace, source-file aliases and independent receiving destinations. The Merchant host retains complete downloads in its configured private export directory. A managed attachment joins the existing Applications listener. An owned attachment starts the maintained Node application and owns its lifetime. The connection is checked against the selected source and actual live instance; choosing another directory is an explicit different attachment.

For an owned paid-native installation, select the original private runtime JSON through the connection's `runtimeFile` setting. Its facilitator configuration passes to the maintained server; the managed connection uses the configuration of its existing listener. Keep those host settings beside the customer's other private runtime references.

The original browser remains useful alongside the agent. A human can inspect the source result, review an edition, examine changes or complete a buyer's payment decision in its established view. The agent performs the corresponding retained product operations and returns their actual identities and results.

## Commission the complete operating course

### 1. Retain the authorised source and approve an edition

Select the native source account and the saved chart. Capture its metadata, complete query responses and subsequent metadata read. Preserve the original query context, native principal, result status, response bytes, saved filters, limits and resolved time window. On an asynchronous deployment, the existing source adapter follows the original job and event cursor.

Choose the actual result query, fields and row identity. Read its projected output and source semantics before recording the named review. Numeric tokens, structured values, nulls, empty strings and absent properties retain the original product's meanings. A source value cannot be reinterpreted merely to produce a visually cleaner report.

The commissioning owner compares the complete selected output with the customer's agreed report. Keep the useful output, original source/edition identity, decision and corrections together in the customer's existing operating case.

### 2. Continue saved operations through the agent

Use one stable operation ID and the current displayed workspace revision for a deliberate mutation. Retain its complete request before dispatch. Inspect the original queued, running or completed operation after an uncertain response; the saved request determines whether that ID can be resumed. A changed request takes a new identity and the current reviewed revision.

The customer can therefore continue a capture, edition selection, named review, comparison or original merchant/buyer action without losing its relationship to the original input. Failure and interruption keep the original progress. The operator can read the saved outcome before deciding on a retry. A repeated request is not a new customer task or purchase.

This course includes an actual recovery on the selected original workspace: interrupt or detach at an agreed safe boundary, reopen the connection, inspect the retained operation, and continue the same request. A customer's live paid operation uses its already selected authorisation, budget and native recovery state.

### 3. Publish and receive the original buyer result

Prepare the approved edition through the existing merchant. Retain its original source, review, dataset snapshot, route and payment terms. Later publication uses the same version store and its guarded refresh, keeping the preceding generation and current revision.

The buyer reviews the advertised resource, chosen payment alternative and total task budget through the original SF88 course. Acquisition retains each page and its actual approval, payment and recovery outcome. A merchant update during acquisition does not change the buyer's selected snapshot.

Receive the completed customer output through the original SF100 exporter. The agreed delivery can include CSV, JSONL, SQLite and selected source material. Inspect the complete output and original lineage. Each later useful purchase has its own approved intent; reopening or transferring the same acquired pages continues their original acquisition.

### 4. Download the full result and editable project

Use the agent's complete export and reading course for a source member, customer file or the whole project. The original result identifies its full bytes and content identity. Retain that export identity while reading all of its content; an interrupted transfer continues the same selected export. The customer receives the complete file rather than a clipped tool response.

The original full-project export carries sources, response bodies, selected editions, named reviews, comparisons, publisher generations, original buyer sessions, delivered files and saved operating history. Exporting preserves the current original native state and the product's source meaning.

Receive that complete project into an independent configured destination through the existing receiver. It verifies and restores the original project, publisher and acquisition using their maintained engines. The receiving engineer inspects both source editions, delivers the acquired baseline, advances one reviewed publisher generation and exports the progressed project.

Reopening the same earlier incoming handover at the first destination preserves that receiving engineer's later work. Another destination can receive the progressed project with its current generations and acquired history. This is the point at which the customer has a maintainable working service and an independent receiving path.

### 5. Close and reopen the actual attachment

Close the agent's current attachment after the active course finishes. Managed close detaches from the existing Applications owner. Owned close drains the application that attachment started. Active request and service lifetime remain with the original product.

Reopen the same report project through its selected owner, inspect the original saved requests and exports, and verify that the customer can continue its next report cycle. The handover identifies the host's source configuration, owning operator, output location, support contact and recovery procedure.

## Acceptance and ongoing service

Acceptance records the actual useful report and complete customer files; source capture and chosen edition; comparison and review; original merchant and acquisition; independent receiving engineer; and actual operating and correction effort. Join each distinct paid transfer to its original facilitator, intent, output and completion time in Delivery operations. The original customer case carries the complete result and subsequent support.

The recurring service begins with the next agreed reporting period or approved source change. The operator captures that edition, compares the same fields and population, reviews the changed report, publishes it through the retained merchant and delivers the customer's selected output. A changed query, field contract or audience is an explicit scope decision. The receiving engineer can operate that cycle from the complete received project.

A support agreement can cover source-access renewal, scheduled report operation, review of upstream schema changes, customer delivery and recovery of the retained service. Define the actual service window, responsible people and recurring output in the customer's workorder. Price that agreed service from its selected operating requirements; this guide creates no additional grant allocation or customer fee.
