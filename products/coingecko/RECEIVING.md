# Install and receive the complete CoinGecko product

Use the maintained selected-source builder, runtime installer, Applications
driver and original project recovery. Customer delivery composes those same
source/model engines.

## Build the selected source

~~~sh
node stellar/scf-starforge-20261009/distribution/build.mjs \
  --repo /absolute/merchant-workspace-checkout \
  --ref COMPLETE_SOURCE_COMMIT --selection coingecko \
  --out /absolute/coingecko-release
~~~

Retain the returned archive, SHA-256, source/installed bytes and source selection.
The package manifest records the exact committed recipe and contributions with
the complete original CoinGecko, browser, MCP, runtime, buyer/seller and
receiving source. Continue an interrupted build in its same output:

~~~sh
node stellar/scf-starforge-20261009/distribution/build.mjs \
  --repo /absolute/merchant-workspace-checkout \
  --out /absolute/coingecko-release --resume
~~~

The original selected build inherits its source and recipe. A different commit
or product uses its own output.

## Install or adopt the original runtime

The complete provider, native buyer and merchant MCP product uses the native,
schema/OpenAPI and MCP/operator profile:

~~~sh
node stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs prepare \
  --dir /absolute/coingecko-runtime \
  --archive /absolute/coingecko-release/RETURNED_ARCHIVE.tgz \
  --sha256 RETURNED_SHA256 --native \
  --feature schema --feature openapi --feature mcp --operator

node stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs install \
  --dir /absolute/coingecko-runtime

node stellar/scf-starforge-20261009/distribution/runtime-install-cli.mjs inspect \
  --dir /absolute/coingecko-runtime --load --source
~~~

Use Node 24 or newer. The original installer resolves the declared package
versions and retained lock. Its supported adoption path can receive an existing
complete dependency graph after original profile, source and lock checks.
The donor remains alive through that borrowing lifetime. Customer receiving
does not initiate another package installation.

The earlier a6b8 operation retains its own d16 source archive and b53
installation. Its actual READY profile is native:true, features:["mcp"],
operator:true with the Stellar SDK16.3.1 pin. That observed legacy profile
remains separate from the full new selected-product profile above. Publishing
this product does not rewrite the earlier archive, failed selection or
installer receipts.

## Managed Applications and the full browser journey

Register the READY installation in the original Runtime workspace. Save the
existing CoinGecko Applications entry with its original market directory,
project and optional private operator configuration. Connect, start and open.

The maintained driver completes seven stages: saved application adoption,
source reads/edits, desktop/mobile browser operation, stop/reopen, interrupted

~~~sh
starforge coingecko-product managed-receive \
  --manifest /absolute/original/applications-receiving.json \
  --out /absolute/original/applications-output
~~~

Use the complete original manifest in
[the maintained receiving guide](../../stellar/scf-starforge-20261009/partners/coingecko-stellar-market/receiving/README.md).
It names the original source/runtime, market/project, existing console and
runtime home, separate recipient, operation prefix, every selected source,
actor and original Playwright/Chromium paths. Existing optional browser
arguments pass through unchanged.

Continue with the same manifest and output. The original driver reconnects
saved requests, reconciles ended workers and controls the original managed
process. This product joins the complete current retained-runtime bootstrap,
Applications recovery driver and guide.

The original paid/provider browser programme remains its existing operation.
Consuming its returned source does not initiate another purchase.

## Create and inspect complete customer work

~~~sh
starforge coingecko-product delivery create \
  --archive /absolute/original-market.json.gz \
  --out /absolute/private/customer-delivery

starforge coingecko-product delivery inspect \
  --directory /absolute/private/customer-delivery
~~~

readProjectArchive validates the full original archive and every original
file/source hash. Delivery preserves that archive verbatim and writes complete
research records, rows, field CSVs, original source blobs, runnable source and
a readable report.

JSONL and field CSV generation proceeds incrementally. The original archive
limits remain 64 MiB compressed and 256 MiB expanded. Each generated file has
a 320 MiB maximum. Exceeding it preserves the original archive and does not
publish a completed delivery manifest.

The original SF88 private-directory lock owns the output writer. On Linux its
existing implementation holds an OS flock. Completed members are immutable:
retries verify identical bytes, continue missing files and publish delivery.json
after the entire output is complete. A changed file is preserved and reported;
a new source edition uses a new directory.

Inspection checks all manifest members, the exact archive identity and counts,
every original source blob and every original runtime file. Its result returns
the complete file and byte counts without changing the delivery.

## Original restore and customer reopening

~~~sh
starforge coingecko-product delivery receive \
  --directory /absolute/private/customer-delivery \
  --state /absolute/private/recipient-market \
  --actor "Recipient operator" \
  --operation original-customer-delivery \
  --name "Received market research"
~~~

The delivery and recipient directories are separate and have no symbolic-link
parents. New private directories are mode0700 and files0600. Receiving uses
the installed original engine; unpacked source is available for inspection
or explicit local operation.

The product verifies the complete delivery, takes the same operator lease as
the browser and CLI, then calls MarketModel.restore. The original transaction
retains the new project, records, all original files, versions, events, complete
ID mapping and operation response.

The receiving checkpoint binds archive/delivery identity, actor, received name,
operation and recipient database inode. If the process ends after the original
transaction commits, a repeat recovers its saved response. Every original
source is verified through the returned mapping before the current recipient
project is returned.

Keep the same directory, operation, actor and name on repeat. A replaced/deleted
original database is reported before another restore. Existing other projects
remain present; later recipient edits are preserved.

Open the browser and select recipientProjectId from the result:

~~~sh
starforge coingecko-product workspace \
  --state /absolute/private/recipient-market --port 0
~~~
