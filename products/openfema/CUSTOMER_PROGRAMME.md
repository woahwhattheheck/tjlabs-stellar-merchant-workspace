# Public Assistance customer programme

Commission OpenFEMA as a complete source-to-customer reporting service for a defined disaster cohort. The installed product retains the official dataset pages, the analyst's decisions, the destination schema, every returned customer row and the original operating history. Its named browser working copies preserve preparation between sessions; the native workspace owns accepted sources, versions, mappings, reconciliations and releases.

The customer's workorder selects the cohort, programme question, receiving system, reporting period, accountable analyst, independent receiving engineer, payer and agreed useful output. A refresh is valuable when it answers that question and produces a usable next edition with its changes explained.

## 1. Select the actual customer job

Use the original [commissioning workorder](../../stellar/scf-starforge-20261009/sf30-seller-sdk/openfema/examples/commissioning-workorder.md). Complete the following selection before adapting a destination mapping.

| Workorder decision | Concrete selection |
| --- | --- |
| Customer question | A named cohort review, assigned follow-up register, source-to-programme reconciliation or later-edition comparison. |
| Cohort | Exact disaster numbers and any portfolio selection criteria; keep declaration geography and applicant location distinct. |
| Source edition | Complete declarations, applicants and obligated-project responses, original retrieval observations and all page bytes. |
| Destination | Actual customer schema or the explicitly labelled neutral staging schema; name the receiving person and their existing system. |
| Analyst fields | Permitted review status, inclusion decision, priority, owner, due date and note; identify who can approve each decision. |
| Useful output | Full mapped project file, complete readable report, customer differences, source references and operating project. |
| Refresh | Trigger or reporting period, input cut-off, changed-source handling, useful-query definition and support expectations. |
| Commercial terms | Agreed workshare or installed merchant terms, payer, asset/network/facilitator, scope and acceptance. |

The complete DR 4724 source supplies a populated commissioning example with 195 obligated projects, 43 applicants and two declaration areas. The October 12 DR 4935 source supplies an early-programme edition with 23 declaration areas and no applicant or funded-project rows. Receive each as its own edition with its own original metadata. An empty funded-project result can still support declaration review and preserve customer records awaiting source publication.

The source is operational reporting data. Funded-project rows describe obligated worksheets. Keep project cost, federal obligations, total obligations and mitigation as four separate measures. Preserve missing amounts, exact decimal values, source IDs, negative corrections and conflicts. The [source contract](../../stellar/scf-starforge-20261009/sf30-seller-sdk/openfema/SOURCE_CONTRACT.md) defines their meanings. A report's source observation does not establish field completion, eligibility, a customer invoice or a procurement deadline.

## 2. Prepare the whole analyst edition

Open the original private workspace through the installed Applications entry or its existing workspace command. Keep the original workspace UUID displayed by the service. Select the correct source, portfolio and saved version.

Name a browser working copy for the actual reporting period or delivery. The working copy retains unfinished mapping JSON, reviewer notes, selected reconciliation rows, publication/payment text, the selected native context and complete original files. Wait for **Saved in this browser** before closing a preparation that has no exported copy yet.

Select each complete source bundle, destination schema and customer CSV through its existing input. The retained-file label identifies the filename and byte length. Reopening the same browser profile restores those full files; a fresh profile receives them through **Export complete copy** and **Import as separate copy**.

Use **Duplicate visible copy** for another proposed preparation. Use **New copy** for a blank one. Native selection changes remain explicit: **Open this copy's saved selection** invokes the original portfolio action when the retained selection differs from the service. Merely selecting or importing a browser copy does not publish data or choose a replacement source.

The [working-copy operating guide](../../stellar/scf-starforge-20261009/sf30-seller-sdk/openfema/WORKING_COPIES.md) describes complete files, storage limits, original request continuation and concurrent windows. Browser preparation and accepted native versions travel together at handover.

## 3. Receive the actual destination schema

In **Data integration**, receive the customer's complete field specification or choose the neutral staging schema. Preserve the original schema file and its exact column names. Use a customer-supplied target designation only for an actual supplied specification.

Every mapping includes disaster number and GM project ID. Their pair identifies one source project across receiving. A source project can support several location-level engineering or programme tasks; retain those customer work-unit identifiers separately. Do not multiply a parent project's financial amounts across its child work units.

Map source IDs and dates as text. Map money to exact decimal source values. Use a null source for customer-owned columns and select the customer key column when the destination provides one. Each writable analyst field has one target column. Repeated read-only projections may be useful for different recipient views.

Save the mapping as an immutable version, then enter the reviewer's name and the field conventions. The review binds the exact mapping hash. A changed mapping is another version with its own review. Its predecessor and supplied specification remain available.

The [complete exchange guide](../../stellar/scf-starforge-20261009/sf30-seller-sdk/openfema/DATA_INTEGRATION.md) supplies the native actions, schema fields and original CLI sequence.

## 4. Deliver and reconcile every customer row

Choose the reviewed mapping and exact saved portfolio version. Export the complete delivery ZIP. It includes the mapped CSV, full native portfolio, mapping and review, original destination specification, source-linked delivery manifest and readable report. Excluded projects stay in the file with their inclusion state; source conflicts and missing required values remain visible.

Receive the customer's full UTF-8 CSV against that original delivery. Preserve its original filename, bytes, BOM if present, hash, extra columns and every row. Inspect the receiving table and complete exported report.

| Receiving result | Programme action |
| --- | --- |
| MATCHED | Retain the agreeing source and analyst values. |
| REVIEW_CHANGES | Select valid analyst decisions for an explicitly reviewed next portfolio version. |
| SOURCE_DIFFERENCES | Compare original source and supplied values; retain their differing values and reference. |
| REVIEW_INPUT_INVALID | Keep the original cells and correct the actual invalid analyst field in a new customer file. |
| UNLINKED_CUSTOMER | Preserve the customer record and resolve its original source identity through the programme's normal work. |
| DUPLICATE_CUSTOMER_ID | Resolve the repeated disaster/project pair before importing its decisions. |
| NOT_OBSERVED_IN_SOURCE_EDITION | Keep the customer identity and the selected source/criteria context; a later source may observe it. |
| SOURCE_ONLY | Review why an observed source project is absent from the customer file. |

Apply only selected valid analyst rows with the receiving analyst and reason. The original action creates one new native portfolio version, carries other decisions forward and binds the original file hash and row. Its baseline check protects concurrent analyst changes. A stale baseline is resolved against the actual current version.

Prepare the next delivery from the resulting version. A same-mapping customer reconciliation may carry uniquely linked customer-owned cells forward. Duplicated or unlinked records and extra customer columns remain in the complete original file included in the handover.

Compare the retained previous and next deliveries. Review newly observed projects, projects absent from the later selection, changed official fields, changed analyst decisions, source/criteria scope and mapping changes. Retain four distinct financial deltas and their missing-value counts.

## 5. Operate the existing merchant and receiving route

The native browser, CLI, original merchant Apps and typed MCP client use the same workspace. The [merchant exchange](../../stellar/scf-starforge-20261009/sf30-seller-sdk/openfema/MCP.md#complete-mapped-project-exchange) accepts declared complete mapping/customer files and drives their original native actions. Keep original operation IDs when continuing a returned or interrupted request.

A browser saves the complete payload before POST. **Handover → Continue retained browser work** asks the full native journal for that same ID. A saved completed result reopens; a pending request continues with its first exact payload. Imported observations remain attached to their original request without creating another native action. Large native objects can be recovered through their original source/customer hashes.

Select the accepted portfolio and publication terms for the commissioned merchant. The existing publisher owns its source version, release, query and payment behavior. Keep reviewer notes and customer-only values in the private project unless the commissioned public projection expressly selects them.

A useful paid query or edition delivers the complete agreed customer output. Resuming the same acquisition or an interrupted download continues the original purchase. Record useful output, actual buyer receiving, later customer use and support in the original workorder. These observations inform the next scope and recurring price.

## 6. Hand over complete source, native project and preparation

The delivery has three related parts:

1. The **customer edition**: complete mapped output, report, customer reconciliation and comparison, original destination specification and source references.
2. The **native operating project**: **Handover → Complete workspace ZIP**, containing source pages, native objects, portfolios, mappings, decisions, publisher history, customer files and original operations.
3. The **unfinished preparation**, where present: **Working copy → Export complete copy**, containing named preparation, exact original files, first payloads and retained outcomes.

Restore the native ZIP through the original importer into an owned receiving directory, preserving its UUID and original journal. Continue an interrupted restore with that same archive and directory. Open the received service and then import the preparation **as a separate copy**. The imported copy is bound to the native workspace; another workspace cannot silently receive it.

Open the agreed report and every supplied attachment, inspect the actual desktop and narrow layout, use the important controls, download the complete files and reopen the delivered project. Select a real earlier customer result and an actual follow-up to establish practical receiving. Correct clipping, unreadable cells, broken links or failed actions in the outgoing edition.

The [whole original receiving course](../../stellar/scf-starforge-20261009/sf30-seller-sdk/openfema/examples/working-copy-receiving.mjs) reuses the completed 195-project workspace. It closes and reopens the browser, retains an actual export across response loss, continues the original request, imports/re-exports a complete copy and preserves edits across a real concurrent-window conflict. It retains its source, input, operation and output bindings on continuation. The [installed receiving guide](RECEIVING.md) identifies the full source and operating course.

If another window changes the browser-store revision, export the visible preparation, reload saved copies and import that export separately. A failed file read, import or storage write leaves the preceding stored copy intact. Preserve the actual error and original files while correcting its cause.

## 7. Commission a recurring installation within the existing grant

This is a source-specific candidate for the original two-merchant/two-buyer cohort. The customer selection determines which installation is commissioned. Record one owner for each source/data preparation, destination mapping, payment deployment, receiving and recurring-support task.

| Existing tranche | Concrete customer result |
| --- | --- |
| T1, days 1–30 | A selected cohort, reviewed destination mapping, deployed host and buyer route, accepted full customer edition and independent operating handover. |
| T2, days 31–90 | The useful operation runs through both selected facilitators; original payment/delivery interruptions recover; the combined plan reaches ten useful purchases by two independent buyers during seven consecutive days ending by day 90. |
| T3, days 91–150 | Recurring mainnet editions, release/rollback and off-host receiving; thirty useful purchases during fourteen consecutive days ending by day 150, both buyers return on another day, and an independent maintainer completes the support case. |

The canonical budget remains USD 38,000, 400 prospective hours and 150 days from award acceptance across its original six packages. Assign a customer-specific adaptation once to the funded package or separately commissioned workshare. The installed product and completed prior source exchange supply a starting point; prospective customer work and actual buyer outcomes retain their own dates and records.

At the end of a period, retain the agreed output, elapsed analyst effort where observed, resolved follow-ups, correction effort, actual receiving outcome and customer feedback. Use that evidence to scope the next useful edition and independent handover.
