## Webhook customer adoption: complete event tasks and operator handover

Our 11 October Mercury/Xycloo outreach proposed implementing one customer's Stellar contract/event family into one existing database or internal API, with source, deployment instructions and receiving-engineer handover. Mercury would retain its subscription and customer relationship; we would implement the selected workflow under its review. The installation begins with the customer's actual recurring decision, source access, destination and accountable operators. A contract activity report, reconciled application table or service exception queue gives a complete event window a useful destination.

The shipped [Webhook event operations product](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/pull/223) supplies signed ingestion, reviewed output fields, separately identified events within a transaction, paid cursor pages, saved buyer operations, NDJSON delivery and complete private operator receiving. An independent buyer collects a fixed event window, applies it to its existing application and returns for a later useful window. Each page retains its actual price and financial outcome; acceptance requires the complete customer task.

The current [commissioning guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/490c84f1b933c5a9733bb1e204c97cabefca6fbb/products/webhook-feed/COMMISSIONING.md) now joins that source and subscriber to a complete customer Analysis destination. The [installed event Analysis guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/490c84f1b933c5a9733bb1e204c97cabefca6fbb/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/python/EVENT_FEED_ANALYSIS.md) and [private browser operating guide](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/cf0a48c99dd896a9dc315b6f9883db850d9f232c/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/python/EVENT_PROGRAMMES.md) give the actual receiving, review, report/workbook, recovery and independent handover paths. The command-line receiver, browser and installed agent workflow use the same original Analysis programme and customer database.

### Receive the whole original event window

The buyer hands over the [original subscriber's](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/490c84f1b933c5a9733bb1e204c97cabefca6fbb/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/event-feed/subscriber.mjs) complete NDJSON export and its original manifest. The [source projector](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/490c84f1b933c5a9733bb1e204c97cabefca6fbb/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/event-feed/analysis-source.mjs) validates their exact bytes, original subscription/store/feed identity, source sequences, individual event identities, payload digests and ordered page history. A complete empty source window is retained as an empty window. A later cumulative export must preserve the earlier accepted events and pages before advancing the source position.

The [Event programmes browser](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/cf0a48c99dd896a9dc315b6f9883db850d9f232c/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/python/stellar_forge_buyer/_analysis_event_programmes_ui.py) receives both original files into the existing private Analysis workspace. Its [receiving coordinator](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/cf0a48c99dd896a9dc315b6f9883db850d9f232c/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/python/stellar_forge_buyer/event_programmes.py) keeps exact file identities, resumable chunks and saved actions in that original SQLite database. A stopped upload continues from its retained offset after the operator selects the same files. The [private HTTP integration](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/cf0a48c99dd896a9dc315b6f9883db850d9f232c/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/python/stellar_forge_buyer/event_programmes_http.py) uses the original Analysis server and its capability to protect this customer application. The local installation selects the trusted receiver code; customer file contents supply data.

The operator names the customer programme and chooses useful payload fields with their actual meanings. Exact decimal or identifier strings remain text. Adjacent state columns distinguish missing values, JSON null and the returned JSON kind, while the complete original payload remains available. Separate events in one transaction retain separate source/event identities. The complete original export, manifest, field mapping and projector source stay attached to the native source document and travel in the whole workspace handover.

### Turn acquired events into editable customer work

The [native Analysis programme](https://github.com/woahwhattheheck/tjlabs-stellar-merchant-workspace/blob/cf0a48c99dd896a9dc315b6f9883db850d9f232c/stellar/scf-starforge-20261009/sf88-operator-buyer-cli/python/stellar_forge_buyer/event_feed_analysis.py) imports an immutable typed table and reviews a later version against the currently accepted customer view. The review records the complete source identity, event and page counts, selected fields, added and retained events, current report/workbook definitions and current source views. The buyer or receiving engineer makes an explicit decision to select that window.

The original query exporter writes every acquired event to typed JSONL and spreadsheet-safe CSV. The original report contains the selected summaries; the workbook includes the full Events sheet and the customer's retained report-backed sheets. Existing worksheet names, notes, conversions and unrelated source sheets remain with their original definitions. If a changed field needs a new worksheet mapping, the operator selects its complete replacement column array through the existing workbook validation. A report's section-size allowance remains a report constraint; it does not turn a full event export into a partial deliverable.

The customer can keep working in the ordinary Analysis application between source windows. When current views or definitions change during an unfinished selected operation, the programme retains the preceding attempt and reviews the customer's current choices before continuing. Saved browser actions retain their original source or review identity before dispatch. Restarted work requires explicit continuation of that same action. This makes a receiving engineer's report edit part of the operating workflow instead of disposable demonstration output.

### Account for a useful paid task

The commercial unit is the useful task the customer agreed to receive. The merchant may price individual cursor pages, while a complete report or application update can require several pages. Installation records the task's actual source scope, completion point, page/resource terms, aggregate spending approval, destination acknowledgment and the source change or elapsed period that makes a later result useful.

Analysis retains each page's original operation ID, complete response identity and recorded native/HTTP outcome. Its event counts describe acquired events. The original buyer and ledger records retain the approved intent, asset/network, exact amount, transfer and financial outcome. The receiving application joins those identities to the accepted complete output when reporting purchases and service use. Reopened files, retried delivery and worksheet revisions remain associated with their original purchase.

The existing two-buyer cohort plan supplies real service days, requests per useful task, completion delays and returning-buyer dates. For this candidate, the commissioning team checks that the actual proposed usage can meet the selected testnet and mainnet windows, including both merchants and both facilitators where required. It selects a credible recurring task and customer population before scheduling the cohort. The original ten-purchase/seven-day and thirty-purchase/fourteen-day targets continue to count distinct qualifying completed purchases through the existing cohort records.

### Hand over and continue the installed service

A complete customer delivery includes the original NDJSON and manifest, reviewed window, typed JSONL/CSV and their manifest, report HTML/JSON/table files, workbook and its original handover, and the whole Analysis workspace archive. The receiving engineer can open the report and workbook immediately, restore the original archive into a separate receiving directory, reopen the saved source and customer edits, and receive a later window through the same programme.

An explicit fresh delivery ID retains the accepted result and creates a new native workspace snapshot. The delivery records both the selected result edition and the programme edition in that actual snapshot. This permits an earlier result to accompany later customer work with clear provenance. Repeating a delivery retains its original archive; preparing a fresh linked delivery after restore selects a new archive operation. The accompanying programme record is extracted from the exact archived database.

The merchant/source operator owns signed ingestion, source authorization, offered terms and publisher recovery. The buyer operator owns its original approval, subscriber acquisition and financial continuation. The customer or receiving engineer owns the selected mapping, accepted application result, current analytical work and independent restore. The service maintainer receives the complete operating state and continues the same Support case when an installation needs correction. The existing commissioning workorder records the people, actual hosts and acceptance decisions for those responsibilities.
