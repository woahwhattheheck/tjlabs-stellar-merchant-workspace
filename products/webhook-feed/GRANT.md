## Customer outcome and accountable roles

Start with the recurring decision or existing application receiving the complete
event task. Record its actual source family, contract/account selection, useful
window, output destination and completion acknowledgment. Agree when a later
window is useful. An event count by itself is an acquired-data fact; the customer
accepts the complete report, reconciled table or application update.

The original Mercury/Xycloo implementation proposal connects one selected Stellar
contract/event family to an existing customer database or internal API and
provides source, deployment instructions and receiving-engineer handover.
The existing company relationship retains its original sender and terms.
The selected installation workorder names the actual commissioning payer and
accepting operator before prospective implementation begins.

| Role | Original responsibility | Work received by the next operator |
| --- | --- | --- |
| Merchant/source operator | Authorized source and signed ingress, event/feed selection, advertised resource terms, source-store retention and publisher recovery | Current source/feed definition, original event identities, reviewed release/terms and source restoration procedure |
